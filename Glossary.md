# Glossary
Revised on 2026-11-11.

Every page, spec and issue of the rewrites uses these names in these senses only, and a new term is agreed before it appears on a page.
The terms outlast the rewrite that brought them in, so they live here rather than on a rewrite's root, and [State in JS](Rewrite-1) brought in these.

| Term | Means |
|---|---|
| Property | A named member of an object: in R, an element of the object's list or one of its R attributes, and in the client, a property of the JSON object, as its TypeScript interface declares it and its JSON Schema lists it, such as a block's `registry_id`, `state` and `name`, or a board's `blocks` and `plugins`. Some properties have a term of their own, as a block's `state` is its block state. A property is never called a field or a key |
| Block class | A value made by `new_block_class()`, defined once and held by the block registry under its registry id, through whose properties R evaluates every block of the class ([Block classes in R](Rewrite-1.1.5#the-block-class)) |
| Block | One instance of a block class, which the board holds as `{ registry_id, state, name, locked }`, and a JSON board with the `version` of its class's state ([Blocks](Rewrite-1.1.1#blocks)). R makes an R block, with the class's constructor, only while it builds a board. A block is never a block class, which is always called one |
| Block state | A block's values for the formals of its class's `expr`, its state args, such as a head block's `n`, which a user sets through the block's UI and the board holds as the block's `state`. It is one of the two sorts of input a block has, beside its data inputs ([Block classes in R](Rewrite-1.1.5#the-block-class)) |
| Data input | One of the inputs a block's class declares in `inputs`, such as a head block's `data`, which a link binds to an upstream block's result. It is one of the two sorts of input a block has, beside its block state ([Block classes in R](Rewrite-1.1.5#the-block-class)) |
| Block registry | R's registry of block classes, filled as the app starts from the block classes that `serve()` takes in `block_classes`, every class of the available packages by default, by `register_block()` for a class that an app script defines, and from the blocks of the board that the script builds, whose entries R sends the client ([Block classes in R](Rewrite-1.1.5#registration)) |
| Registry id | A block class's id in the block registry, `{pkg}-{id}`, of its package and the id that `new_block_class()` takes, such as `blockr.core-head_block` |
| Available package | A package that exports `._BLOCKR_MODULES_`, among the installed packages that depend on blockr.core and those that `pkgload::load_all()` loaded, whose block classes an app offers and whose plugin classes it runs unless its script narrows them, as `available_blocks()` and `available_plugins()` list them ([Block classes in R](Rewrite-1.1.5#registration)) |
| Block expression | The R expression R evaluates for a block, whose result R keeps under the block's id, and an exported script holds for it, without the assignment to the block's id that the script adds, which interpolation makes from what its class's `expr` returns: with the upstream blocks' ids in place of the placeholders of a `blockr_expr`, and otherwise as a function of the block's data inputs called with those ids ([Block classes in R](Rewrite-1.1.5#expressions)) |
| Placeholder | A data input written as `.(data)`, or a variadic block's inputs as `...`, in what `bbquote()` returns, or as another class that inherits from `blockr_expr` writes them, which interpolation replaces with the upstream blocks' ids ([Block classes in R](Rewrite-1.1.5#expressions)) |
| Interpolation | Filling in placeholders such that we get a quoted expression that can be evaluated in the context of data, the block expression: R calls a class's `expr` with the block state, and the generic `interpolate()` turns what `expr` returns into the block expression, dispatching on its class ([Block classes in R](Rewrite-1.1.5#expressions)) |
| Command registry | The client's registry of commands ([Board updates](Rewrite-1.1.2#commands)) |
| Board | The client's board, the JSON object the store holds, with core's properties, its plugins in `plugins` among them, and no class of its own ([Board objects](Rewrite-1.1.1#the-board)) |
| Plugin | What extends a board as a whole, core's one way to extend a board besides block classes, of which an app runs at most one of each plugin class, identified by the class's id and named by its class, and whose state, where its class has any, the board holds under that id in `plugins`, in place of board classes, core's plugins of today and the dock's extensions. In R it is an S3 object of class `c("{name}_plugin", ..., "plugin")`, which a package's constructor `new_{name}_plugin()` returns and a board constructor takes in `plugins` for its state alone, while `serve()` takes the app's plugins, which run on every board that the app opens, as rows in `plugins`, each a plugin class by its package and id ([Plugins](Rewrite-1.1.12#which-plugins-a-board-has)) |
| Plugin class | A class of plugins, by the id that its package declares, in full `{pkg}-{id}`, such as `blockr.dag-dag_plugin`, and with a name, the id's human-readable form, such as "Document" for blockr.md's `md_plugin`, which the package's startup module registers in JS as a `PluginClass`, setting any mix of its members: the board options it requires, the schema and default of its plugins' state, one function that keeps that state consistent with the rest of the board and one that migrates it, its `ui`, its `frontend`, its `storage` and its `start`. In R, the package lists the class in its `._BLOCKR_MODULES_`, with its id, its constructor and its name, and gives the version of its state through its method of `plugin_version()` and its requests through `plugin_requests()` ([Plugins](Rewrite-1.1.12#a-plugin)) |
| JSON board | The one format of a board outside the store, `{ format, packages, board }`: the board with every id, its collections keyed by id, each block with the version of its class's state, each board option's value with the version of its shape and the board with the version of each plugin class whose plugins it holds, beside the version of the format and the versions of the packages its content comes from, which name what to install. The client saves a board as one, and R writes the opening board as one ([Serialization](Rewrite-1.1.4#files)) |
| Conversion | Turning a file of today's stack, which has no `format`, into a JSON board, once and in R, by blockr.convert's `convert_file()` with the `blockr_deser()` methods that the packages that wrote such files register on it ([The conversion and the migration notes](Rewrite-1.9)) |
| Migration notes | A package's vignette that lists each change that an app script calling the package needs at the switch, with what takes the place of each function that goes, written so that an AI can apply it ([The conversion and the migration notes](Rewrite-1.9#the-migration-notes)) |
| Store | The TypeScript object in core's JS API that holds the board and applies every change to it as a delta, which it can undo but for a board option's value and the deltas of a command with `undo: false`, one per board, which core creates and hands to plugins and modules through `CoreApi` and their hosts ([Board updates](Rewrite-1.1.2#the-store)) |
| R board | The R object that an app script's constructors build, and that R drops once it has the board's JSON |
| Board option | An option the user sees and changes while the app runs, meant above all for how the board is shown, such as `n_rows`, the number of rows on a page of a table output. It is no substitute for plugin state, where a setting of a plugin's own goes first. It is an `Option` in the client, with an `id`, `label`, `category`, `schema` and `ui`, which the package that ships it defines in the client. Core resolves its default when the client first needs a component that requires it, such as a renderer, while the board holds a value under its id only once a script, a file or a command sets one. Unlike a blockr option, it changes while the app runs, and a value that someone set is saved with the board, while undo never takes it back ([Board options and blockr options](Rewrite-1.1.13)) |
| Blockr option | A value fixed when an app starts or is deployed, which `blockr_option()` reads from an R option `blockr.<name>` or an environment variable `BLOCKR_<NAME>`, and which the board never holds. Unlike a board option, the user never changes it, and no file saves it ([Board options and blockr options](Rewrite-1.1.13#blockr-options)) |
| Plugin state | What a plugin keeps in the board, as a block keeps its block state, such as the dock's views, the DAG's positions, blockr.md's document or the assistant's threads, in the shape that its class's schema gives, which is saved, undone and migrated with the board and open to external control. A setting of the plugin's own goes here first, since a board option is meant above all for how the board is shown ([Plugins](Rewrite-1.1.12#a-plugins-state)) |
| External control | Setting a block's state or a plugin's state from outside what owns it, as a drill sets a cohort filter's condition, or as the assistant edits a block, arranges the dock's views or moves the DAG's positions, through the commands that set them, core's among them, to which every block and every plugin is open on a board that is not locked ([Board updates](Rewrite-1.1.2#commands)) |
| Frontend | A plugin whose class has `frontend`, the module that draws the page, such as the dock, whose module a package offers in R under a name, giving it an id such as `blockr.dock-dock`, and whose class in R extends `frontend_plugin` and has a method of `frontend_args()`, which takes the arguments of `serve()` that core does not take, such as the dock's `navbar`. An app has one, which runs on every board that it opens, core's basic frontend unless another available package gives one, while a block that `serve()` serves alone has no frontend ([Plugins](Rewrite-1.1.12#the-frontend)) |
| Storage plugin | A plugin whose class has `storage`, which gives the controls that every frontend draws, such as session management's, and whose class in R extends `storage_plugin`. An app has at most one, through which every board that it opens saves, core's own unless another available package gives one, whose controls Save and Open save a download and open an upload, while a frontend draws no storage controls in an app that has none ([Plugins](Rewrite-1.1.12#storage)) |
| Storage controls | What the `storage` of a storage plugin's class gives every frontend to draw, with the frontend's own components: buttons, menus and statuses, in the plugin's order, such as core's Save and Open, and session management's menu named after the workflow, its save status and its Save menu. They are the only part of the page that a storage plugin gives a frontend to draw, and what they cannot hold, the plugin draws in a dialog of its own ([Plugins](Rewrite-1.1.12#storage)) |
| View | One page of the dock, with an id that never changes and is unique among the views, a name that the user picks and may change, the folder it sits in, if any, and a grid ([The dock's state](Rewrite-1.2.1#views-and-folders)). The dock plugin's state holds each view under its id. The dock shows one view at a time, the active view, which its state names and which a board opens on. A block or a plugin may have a panel in several views. Dockview's `views` are something else: the panels of one of its tab groups |
| Folder | A place in the dock's navigation that holds views and other folders, with an id that never changes, a name that the user picks, and no grid of its own. The dock plugin's state holds each folder under its id, and each view and folder names the folder it sits in. Folders only group and order the navigation: what a view shows never depends on its folder ([The dock's state](Rewrite-1.2.1#views-and-folders)) |
| Grid | How the panels of one view are arranged, as the dock stores it: splits, each dividing its space among its children by ratios that sum to 1, tab groups at their ends, and rails on the view's left and right edges. It alone says which panels the view shows. It is the dock's own format, not dockview's layout: the dock makes dockview's layout from a grid to draw the view, and reads it back into a grid after each change of arrangement, so no board depends on dockview. An app script writes one with `dock_grid()` ([The dock's state](Rewrite-1.2.1#grids)) |
| Tab group | Panels that share one place in a view and show one at a time, with a tab for each, at an end of a grid's splits or in a rail. In today's R, `panels()` writes one, while `group()` writes a split ([The dock's state](Rewrite-1.2.1#grids)) |
| Rail | A tab group pinned to the left or right edge of a view, outside its splits, which the user collapses to its tabs and opens again. Its width is in pixels, as for dockview's edge groups ([The dock's state](Rewrite-1.2.1#grids)) |
| Panel | Where a view shows one block, in its card, or the UI of one plugin whose class has a `ui`, as a tab in a tab group. A grid names a panel by what it shows, as `{ "block": "a" }` or `{ "plugin": "blockr.dag-dag_plugin" }`, and a view has at most one panel for each block or plugin ([The dock's state](Rewrite-1.2.1#grids)) |
| Navbar item | An entry of the dock's bar, which the app script gives `serve()` in `navbar`, in its order: one of the dock's own parts, the storage plugin's controls or one of them apart, a spacer, a link, a menu, or a JS module that draws the item. No board or file holds them, and no plugin adds one by itself ([The dock's navbar](Rewrite-1.2.5#what-the-bar-holds)) |
| Startup module | The one module a package may declare in R for what has to run before anything mounts, which core initializes with `CoreApi`, one package at a time in the order of their R dependencies, before the frontend mounts and before the store opens a board ([UI modules in JS](Rewrite-1.1.7#startup-modules)) |
| Output | An S3 object of an output class, which the class's coercion makes from one result and R sends as JSON, naming the renderer that draws it ([Block classes in R](Rewrite-1.1.5#outputs)) |
| Output class | An S3 class of outputs, whose class vector ends in `block_output`, such as `table_output`, which a block class names by its coercion, another package extends with a subclass, and the package that defines it gives a constructor, `new_table_output()`, a coercion that makes an output from a result, `as_table_output()`, and, through its methods of `output_schema()`, `output_requests()`, `output_renderer()` and `output_coercion()`, the JSON Schema that R writes its outputs by, requests that its renderers call, such as a download, the renderer that draws its outputs unless an app names another, and the coercion that makes them, by which R names that renderer in a block class's registry entry ([Board options and blockr options](Rewrite-1.1.13#the-renderer-before-the-first-output)), all of which S3 dispatch gives a subclass unless it gives its own, beside a contract that its renderers are written against: the schema with their TypeScript type, the types of their parameters, of the events its renderers emit and of its requests, the board options its coercion reads, and fixtures ([Block classes in R](Rewrite-1.1.5#outputs)) |
| Renderer | A module that draws the outputs of an output class or a board option's value, as an object that `new_renderer()` makes in R, with the module, whose code names the board options it requires, its id, `{pkg}-{name}`, and its own requests, beside those of its output class. An output class's renderer is the one that its method of `output_renderer()` gives, and an app replaces it, or a board option's UI, only by naming another renderer in the blockr option `renderers`, which the method reads. R puts in each output the renderer that draws it, with where it serves the renderer's module ([Drawing the board](Rewrite-1.1.8#renderers)) |
| Lock | What an app fixes, by one of three locks, each set on its own: the load lock, the blockr option `lock_load`, fixes the app to its opening board; the board lock, the blockr option `locked`, fixes what a board holds but its blocks' state, its board options and its plugins' state; and a block's lock, its `locked`, fixes the block's state under the board lock, which `null` follows. The store refuses what they fix, and R refuses an evaluation that rebinds a block's data inputs or gives a locked block another state, holding every block to the opening board where the load lock is on too, so that no client can loosen them, while a plugin, a frontend among them, may lock more of what it alone keeps, such as the dock the arrangement of its panels ([Locked boards and the properties of blocks](Rewrite-1.1.11#three-locks)) |
| Transport | What carries the wire protocol's messages, and the binary bodies beside them, between the client and R. On the page that is Shiny, through the Shiny transport, a module on each side, `shiny_transport()` in R and `shinyTransport()` in the client, which is all that leaving Shiny replaces, and in tests it is the protocol's fixtures ([Wire protocol](Rewrite-1.1.9#the-shiny-transport)) |
| Request | What the client asks R for an answer, rather than for a block's result: a function that a block class, an output class, a renderer, a board option or a plugin gives in R, which R answers by the request's type, finding it by that object's id, a plugin's by its class's id, or an output class's by the output it names ([Wire protocol](Rewrite-1.1.9#requests)) |
| Demand | What an owner asks the scheduler to keep evaluated, a set of blocks or a function of the board, until it releases it. The scheduler evaluates every demanded block and what feeds it, while a one-time evaluation brings some blocks up to date once ([Evaluation in the client](Rewrite-1.1.10#demand)) |
| One-time evaluation | What brings some blocks up to date once, without keeping them evaluated, and resolves with their statuses, or, given parameters, runs them even where they are current ([Evaluation in the client](Rewrite-1.1.10#demand)) |
| Parameter | A value that a request, an output request or a one-time evaluation passes besides the block's state, such as the column whose values a dropdown lists, a save's `save` or the page a table output shows, which `expr` never sees and the board never holds ([Block classes in R](Rewrite-1.1.5#requests)) |
| Evaluation priority | A number that every demand and one-time evaluation carries, 0 by default, by which the scheduler orders evaluations, and where an evaluation below 0 gives way to whatever waits behind it ([Evaluation in the client](Rewrite-1.1.10#demand)) |
| Recipe | What an evaluation request carries for a block: its registry id, its state, and its inputs as upstream blocks and revisions, in the order of its class's inputs, from which R builds the block expression ([Wire protocol](Rewrite-1.1.9#evaluating-a-block)) |
| Revision | A block's number in the scheduler, which goes up whenever the block's recipe changes or something invalidates it, as a new session does for every block, never goes back within the page, and names the block's result in R, unlike a version, which is always a package's, the protocol's, a JSON board's format, or a shape's, the version that a block class gives its state, a plugin class the state of its plugins and a board option its value, by which a JSON board migrates ([Evaluation in the client](Rewrite-1.1.10#revisions)) |
| Edit id | What the store keeps for each block and for each plugin, which only their own edits change, and which a delta names so that the store refuses it where another edit came first ([Board updates](Rewrite-1.1.2#deltas)) |
| Notification | A message, warning or error that the user should see, whoever raised it: R, as a condition while it evaluates a block or makes its output, core, where it fails at something that the user asked for or that the board needs, or a plugin, the frontend among them. Core holds every notification of the open board in the `notifications` member of `CoreApi`, outside the board, each with its severity, class, origin and what it concerns, until its cause goes, and the frontend decides how each shows and for how long. Unlike a condition, which R raises, or an exception, which the client throws, a notification is what reaches the user, while what fails and reaches no user is logged ([Notifications, logging and tracing](Rewrite-1.1.14)) |
| Logger | What writes log lines out, never what a package calls: in R the function that the blockr option `logger` picks, such as `cat_logger()`, which writes to standard output and standard error, or `otel_logger()`, which writes through OpenTelemetry, and in the client the console's or OpenTelemetry's, which the blockr option `otel_client_endpoint` picks. A package writes log lines through `write_log()` in R and through `log` in the client, and a deployment swaps the logger without changing a package ([Notifications, logging and tracing](Rewrite-1.1.14#logging)) |
