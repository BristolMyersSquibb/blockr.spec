# Assistant as a client extension
Status: draft. Part of [State in JS](Rewrite-1).

This part covers blockr.assistant, which becomes a plugin whose agent loop runs in the browser.
It builds on the plugins, commands, scheduler and requests of [Client-owned board state](Rewrite-1.1), on the dock's commands for the views it arranges today ([Client-drawn dock](Rewrite-1.2)), and on blockr.ui's design system for its look ([UI kit and design system for the client](Rewrite-1.7)).

## Problem

Today's assistant runs its agent loop in the session's R process through ellmer, with 40 tools (`ellmer::tool()` definitions at `fd58655`) that change a running Shiny board.
Its mutation tools stage a delta ([`commit_pending()`](https://github.com/BristolMyersSquibb/blockr.assistant/blob/a429c3061348a354834eeb2a5c173f8ff27f7c0b/R/stage-pending.R#L88)), and its `commit` tool applies it through the board's `update()` ([`flush_pending()`](https://github.com/BristolMyersSquibb/blockr.assistant/blob/a429c3061348a354834eeb2a5c173f8ff27f7c0b/R/stage-pending.R#L682)) and waits for the touched blocks to re-evaluate, up to `assistant_commit_timeout_secs`, 30 s by default; a commit can also stop partway, with "the board may be partly updated" ([`tools-commit.R`](https://github.com/BristolMyersSquibb/blockr.assistant/blob/fd5865593fd8b015d00df9238e2e622475c2a9df/R/tools-commit.R#L84-L116)).
With the board held by the client ([Client-owned board state](Rewrite-1.1)), there is no R board to stage into, and the assistant's edits and the user's meet in one board.

## What must hold

1. The assistant is a plugin, which works under every frontend ([Plugins](Rewrite-1.1.12#what-must-hold)), and whose edits go through core's command registry, each applied all or none and marked as its own, so that undo keeps its steps apart from the user's ([Board updates](Rewrite-1.1.2#what-must-hold)).
2. An edit reports done only once the blocks it changed, and those downstream of them, are current, with each block's status and conditions.
3. The loop works with the visitor's own credential as with one that R obtains or the deployment provides, and nothing in it changes to switch between them.
4. A turn keeps going while the assistant's panel is closed or its tab is hidden, until the browser discards the page.
5. What blockr.assistant offers today carries over, but for what Today drops with its reason.
6. Boards saved with today's assistant open with its threads, as condition 4 of [State in JS](Rewrite-1#what-must-hold) asks.

## Proposal

- The assistant is a plugin of one class, `blockr.assistant-assistant_plugin`, named Assistant, which blockr.assistant's startup module registers ([Plugins](Rewrite-1.1.12#a-plugin)).
  Its state holds the threads, its `ui` draws the chat in whatever place the frontend gives it, and its `start` runs each turn, so that a turn goes on once the panel closes ([Plugins](Rewrite-1.1.12#running-a-plugin)).
  Its method of `plugin_requests()` gives what needs R or the server's files: the summary of a block's result through `describe_result()`, and the list of skills and the text of each ([Plugins](Rewrite-1.1.12#a-plugins-requests)).
  An app script makes it with `new_assistant_plugin()`, which takes the threads of a board that the script builds.
- The agent loop runs in the browser, where the board it edits is, with the commands that core and the packages of other plugins register, and requests to R, as its tools, so that it changes another plugin's state, such as blockr.md's document or the DAG's positions, through that plugin's commands or core's `blockr.core-set_plugin_state`, as it changes core's objects through core's commands ([Plugins](Rewrite-1.1.12#a-plugins-state)).
  It reaches the board only through `CoreApi`, never the DOM, so that it could run in Node on the server the [Roadmap](Roadmap#a-server-of-our-own) considers.
- The tools that read the board run in the browser, on the board, the block registry and each block's status, conditions and summary ([Drawing the board](Rewrite-1.1.8#what-core-gives-plugins)).
  A tool that reads a block's result sends a request of the plugin that reads the block, which R answers through `describe_result()`, so that a package that teaches the model about a class of results keeps giving a method of that generic in R, as blockr.sandbox does for its composer tables.
- Two libraries run such a loop in a browser, and a spike chooses between them (Work): the AI SDK, `ai` with a provider package such as `@ai-sdk/anthropic`, and pi, `@earendil-works/pi-agent-core` with `@earendil-works/pi-ai`, while a provider's own SDK would leave the loop to us.
  The spike builds the edit tool, one request to R and compaction on each, with OpenAI's provider, which both apps that use the assistant today chat through (Today), and with Anthropic's.
  It keeps the library that does the following with less code of our own, the smaller bundle breaking a tie: it meets What must hold 1 to 4, streams a turn and stops it when the user does, takes the JSON Schemas that core and other packages register as tool schemas unchanged, goes on with a thread once its board is saved and opened again, and runs under Vitest on happy-dom with the model faked.
- The assistant pays for nothing but the model provider's tokens for now, so it uses no hosted service, such as Vercel's AI Gateway (notes) or assistant-ui's Assistant Cloud.
- The assistant ships the `llm_model` board option, which core defines today ([R/board-option.R#L666-L751](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/board-option.R#L666-L751)) and only the assistant reads, and defines it in the client as every package defines the board options it ships ([Board options and blockr options](Rewrite-1.1.13#defining-a-board-option)).
- One edit tool takes a whole delta and applies it as one undoable step, rather than one tool per command, as Anthropic's guidance argues: "More tools don't always lead to better outcomes" ([Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- The edit tool evaluates the blocks it changed and everything downstream of them, those no panel shows included, in a one-time evaluation ([Evaluation in the client](Rewrite-1.1.10#demand)), and returns once they are current, with each block's status and conditions, so that it sees every failure it caused, and a block the user edits meanwhile at its newer revision.
- A reply streams in the plugin's memory and enters its thread, in the assistant's plugin state, as one finished message, since a delta per token would reach every follower, as a delta per keystroke would ([Board updates](Rewrite-1.1.2#undo)).
  The commands that change a thread have `undo: false`, whoever wrote the message, so that no undo takes a message back and no message takes an undo step ([Board updates](Rewrite-1.1.2#undo)).
- While a turn runs, the assistant holds a Web Lock named for its tab, since Chrome freezes a background tab, which stops its tasks and fails its WebSockets, unless it holds one ([workadventure#6740](https://github.com/workadventure/workadventure/pull/6740)).
  Nothing on a turn's path waits on chained timers, which a tab hidden for five minutes runs once a minute, or on animation frames, which a hidden tab never runs ([timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)).
- The plugin loads its loop and its provider code with a dynamic import as the first turn starts, since they weigh 116 to 205 KB gzipped (notes), which a page where nobody asks the assistant anything never needs.
  A panel that shows is no sign of that, since a board's default view in the dock holds every plugin's panel on its left rail ([Places the dock offers plugins](Rewrite-1.2.4#a-plugins-panel)).
- The loop takes its credential through one function that the library calls for each request, a `fetch` of its own in an AI SDK provider and `getApiKey` in pi, so where it comes from stays open (below).
  What a visitor can take is no downside of the client: any visitor who can use the assistant can take a credential it uses, today as after the switch, since a visitor runs R through a block that takes their code, as core's subset block takes its `subset` and `select` ([R/transform-subset.R#L29-L31](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/transform-subset.R#L29-L31)), and through the assistant, which writes such code when asked and reads the block's output.
  A credential in the browser only makes that visible.
  Limiting it stays the deployment's job ([State in JS](Rewrite-1#proposal)), which matters most for an app on the public internet, whose visitors are anyone.

## Open questions

- Whether the edit tool takes a whole delta, which it applies with `store.apply()`, as the Proposal has it, or a list of commands, which it plans and applies as one step.
  [Board updates](Rewrite-1.1.2#commands) has the assistant's tools edit through the command registry, as its condition 4 asks, with `commands.plan()` as their staging.
  On `js-state`, though, `commands.plan()` checks each command against the current board ([srcts/commands/commands.ts#L191-L194](https://github.com/BristolMyersSquibb/blockr.core/blob/7ed8eee9769a1e65addf4af0ddd866cda8357844/srcts/commands/commands.ts#L191-L194)), and `blockr.core-add_link` is enabled only where both of its blocks are on the board ([srcts/commands/core.ts#L337-L358](https://github.com/BristolMyersSquibb/blockr.core/blob/7ed8eee9769a1e65addf4af0ddd866cda8357844/srcts/commands/core.ts#L337-L358)).
  So an edit that plans its commands one at a time cannot add a block and link it, which today's staging allows, since it counts the blocks staged before ([R/stage-pending.R#L254-L283](https://github.com/BristolMyersSquibb/blockr.assistant/blob/fcbdb2756a8965915159b7b5ec51197ae458c2c8/R/stage-pending.R#L254-L283)).
  It blocks the edit tool and the Work item that rebuilds the assistant, and choosing one of the two, with what it changes in core's command registry or in condition 4 of Board updates, settles it.
- Whether an answer that needs a number adds a block, so that every number the assistant reports is in the exported code, or the assistant may go on running R outside blocks, as `inspect_results` does today.
  It blocks the requests of the assistant's plugin, and deciding whether an exported script has to hold every number that the assistant reports settles it.
- How the browser gets its credential: the visitor's own key, a token R obtains for the visitor, a short-lived token R mints, or a key of the app's that R hands over, with the proxy in R only for a provider that visitors' browsers cannot reach (notes), or a key that the server the [Roadmap](Roadmap#a-server-of-our-own) considers holds out of R's reach.
  Both apps that use the assistant today keep an OpenAI key in R's environment (Today), and OpenAI's short-lived tokens serve only its realtime API (notes), so for them the choice is between a key of the app's that R hands over, the proxy in R and the visitor's own key.
  It blocks the last Work item, not the loop (What must hold 3), and choosing which of these the assistant supports first settles it.
- Whether the assistant keeps `llm_model`, `chat_compact_tokens` and `chat_compact_keep` as board options, as today, or in its state, since a board option is meant above all for how the board is shown, and a setting of the assistant's own goes in its state first ([Board options and blockr options](Rewrite-1.1.13#the-two-kinds)), and how an app names the models it offers, which today's blockr option `chat_function` gives as ellmer's chat functions, which no browser can call.
  It blocks the item of the Proposal on `llm_model`, and weighing each of the three settles it.
