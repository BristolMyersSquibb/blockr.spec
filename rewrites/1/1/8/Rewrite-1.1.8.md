# Front-ends and extension points for the client-owned board
Status: settled on 2026-10-30. Design for [Client-owned board state](Rewrite-1.1).

One of the API proposals for the client-owned board ([Client-owned board state](Rewrite-1.1)): core's basic front-end, how a front-end such as blockr.dock replaces it, and what front-ends and their extensions hook into. It builds on the [board objects proposal](Rewrite-1.1.1) and on the [board updates](Rewrite-1.1.2), evaluation ([Evaluation in the client](Rewrite-1.1.10)) and UI modules ([UI modules in JS](Rewrite-1.1.7)) proposals, and shapes front-end registration and `CoreApi`, renderers, core's basic front-end and removing the generics that draw UI from R, each an item in the Work list of [Client-owned board state](Rewrite-1.1#work). The dock's contribution points, such as its panels, navbar items and sidebar sections, are [Client-drawn dock and extensions](Rewrite-1.2)'s.

## What must hold

1. Core ships a basic front-end that draws any board, so a board serves without blockr.dock, and a front-end replaces it entirely, so that none of it runs underneath another, as core's stack generics run underneath the dock today.
2. A front-end draws everything around a block, its card, panel, menus and status, while core mounts the block's UI and output, so a block class works in every front-end.
3. A front-end and its extensions work on the board only through core's JS API: the store, commands, demand, statuses and requests.
4. Nothing in R draws or redraws UI.
5. A front-end or any other package can replace the renderer that draws an output class or a board option, and an app picks among them through a blockr option, with no change to a block class.
6. A startup module can open another board in place of the opening board before anything is drawn or evaluated, as `rack_loader()` resolves the board a URL names before today's page is drawn.
7. Opening a board leaves the page as serving that board in a fresh app would, its front-end included, as a restore does today, but with no reload.

## Today

Core's front-end is `board_ui.board()`: a toolbar of its plugins with a popover of board options, a bslib accordion of stacks and a bslib card per block, whose header and footer the `edit_block` plugin draws ([R/board-ui.R#L40-L140](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/board-ui.R#L40-L140)). It computes a block's status without drawing it, and shows conditions as notifications ([R/plugin-notification.R#L76-L140](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/plugin-notification.R#L76-L140)). It parks the blocks of collapsed stacks through `gate_stacks()`, the default `callbacks` of `board_server()`, so a stacked board is lazy under it ([R/board-server.R#L143-L158](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/board-server.R#L143-L158)). A front-end replaces it by implementing generics that dispatch on the board, `board_ui()`, `block_ui()`, `insert_block_ui()`, `remove_block_ui()` and more, and by passing `callbacks` of its own: blockr.dock implements those four and `blockr_app_ui()` and `blockr_app_server()`, through which it passes its callbacks ([blockr.dock R/utils-serve.R#L64-L86](https://github.com/BristolMyersSquibb/blockr.dock/blob/fd806ec45fd7158c32ae13b59cdca9386f34a985/R/utils-serve.R#L64-L86)), but none of the stack generics, which still fire underneath it ([R/stack-ui.R#L37-L255](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/stack-ui.R#L37-L255)). The board's class also picks the page: `serve()` builds it with `blockr_app_ui()` for the board its loader returns at each request, and a restore stages the restored board and reloads the page, so a core board restored in a dock app brings core's UI along ([R/utils-serve.R#L227-L288](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L227-L288)). Extensions hook in through `new_dock_extension()` and `extension_block_callback()`, which the DAG uses to draw status badges ([R/ext-class.R#L52](https://github.com/BristolMyersSquibb/blockr.dock/blob/fd806ec45fd7158c32ae13b59cdca9386f34a985/R/ext-class.R#L52), [blockr.dag R/ext.R#L521-L583](https://github.com/BristolMyersSquibb/blockr.dag/blob/68869c56f83a0ec0c4987c75e9a1c07a46cf529b/R/ext.R#L521-L583)). Insertions and removals reach the page through R, and the dock's removal currently misses: the selector it passes to `removeUI()` is built from the board's id instead of the block's and lacks the `#`, so it matches no element, as [blockr.dock#527](https://github.com/BristolMyersSquibb/blockr.dock/issues/527) reports ([R/block-ui.R#L104](https://github.com/BristolMyersSquibb/blockr.dock/blob/fd806ec45fd7158c32ae13b59cdca9386f34a985/R/block-ui.R#L104)).

## Proposal

### Registering a front-end

A front-end is a module that a package declares in R under a name when it loads, as a block class names its UI module, so that its id is `{pkg}-{name}`, as a registry id is, and a package can ship several. The declaration also names the board class the front-end draws, and the board options it requires, which R gives a board it opens as JSON, since such a board has no class for `board_options()` to dispatch on ([Defining a board in R](Rewrite-1.1.3#options)):

```r
register_front_end("dock", js_module("dock.js"), class = "dock_board", options = dock_board_options)
```

The dock is then `blockr.dock-dock`, and core's basic front-end is `blockr.core-basic`, which core declares for `board`. A board names the front-end it is made for by that id in its `front_end.id`, which R picks wherever it holds the board as an R object, the one an app script builds and the one `blockr_deser()` builds from a file of today's stack: it takes the front-end declared for the most specific class in the board's class vector, as it picks a renderer for an output (below), so that a board class extending `dock_board` that no package declares a front-end for is drawn by the dock, and every board by core's basic front-end at least. Two front-ends declared for one class are an error naming both, and a board given as JSON keeps the id it holds, since it carries no class ([Board objects](Rewrite-1.1.1#the-board)).

R tells the client where each front-end's module is served, by the front-end's id, as it does for every module a package declares ([UI modules in JS](Rewrite-1.1.7#packaging)), and every board is drawn by the front-end it names: core imports the module of the first board's front-end once every startup module has initialized, and switches the page in place to the front-end a board opened later names (below). A front-end fills in its own state where a board lacks it, from its package's migration ([Board updates](Rewrite-1.1.2#the-front-ends-state-and-attributes)), and R drops and names the state of a package that is not installed ([Board objects](Rewrite-1.1.1#objects-that-cannot-be-rebuilt)). Nothing in R converts a board, and R never needs a board's constructor to open one, nor builds a board to learn about a front-end.

The module meets the contract a block's UI module meets ([UI modules in JS](Rewrite-1.1.7#the-contract)), with `CoreApi` in place of a host: it exports the JS API major it was built against and a default whose `render()` core calls, so it never names its own id.

```ts
export const api = 1;                                // the JS API major it was built against

export default {
  render({ el, core, signal }: { el: HTMLElement; core: CoreApi; signal: AbortSignal }): () => void { /* draw the board, return the cleanup */ }
};
```

### What core gives a front-end

```ts
interface CoreApi {
  store: Store;                    // board(), subscribe(), apply(), open(), register(), from Board updates
  commands: Commands;              // run(), plan() and the command registry, for menus and shortcuts
  scheduler: Scheduler;            // demand(), evaluate(), invalidate(), status(), subscribe(), from Evaluation in the client
  blockRegistry: BlockRegistry;    // the block registry's entries by registry id, for pickers
  options: Options;                // register() and the board options packages define, by id
  blockrOptions: BlockrOptions;    // the blockr options the client reads, by package, from the reply to hello
  lock: Lock | null;               // the blocks a locked board leaves open, { open: ["f"] }, from the reply to hello
  outputEvents: OutputEvents;      // what renderers report the user did, such as a selection, for extensions to act on
  request<T = Json>(extension: string, name: string, args?: Json, opts?: RequestOpts): Promise<T | Blob>;   // an extension's request, by the extension's id
  module<T = unknown>(id: string): Promise<T>;                // a module another package offers, by id
  mountBlock(el: HTMLElement, block: BlockId): () => void;    // the block's UI module
  mountOutput(el: HTMLElement, block: BlockId): () => void;   // its output, measured, fetched and drawn by the renderer R names in it
  mountOption(el: HTMLElement, option: OptionId): () => void; // a board option's UI, or the renderer R picked for it
}

interface RequestOpts {
  reads?: BlockId[];                                         // the blocks it reads, which core has evaluated first
  signal?: AbortSignal;                                      // cancels it, as a cancel does on the wire
  progress?(note: { value?: number; message?: string }): void;   // each progress note R sends for it
}

interface OutputEvents {
  subscribe(fn: (event: { block: BlockId; name: string; payload: Json }) => void): () => void;   // each event a renderer emits ([UI modules in JS](Rewrite-1.1.7#the-contract))
}
```

A front-end decides where things go and core fills them: it gives `mountBlock()` the body of a card or a panel, and core mounts the block's UI module there, so the dock's card sections stay the dock's business while what is in them stays core's. A front-end may mount a block's UI or output in several places at once, such as two panels of one view, and mount it again as its panels move or reopen, since everything a mount draws from is core's and none of it is lost when a mount ends ([UI modules in JS](Rewrite-1.1.7#the-contract)), rather than moving one element around, as the dock parks each card in its offcanvas today and carries it into a panel and back ([blockr.dock R/block-ui.R#L188-L295](https://github.com/BristolMyersSquibb/blockr.dock/blob/fd806ec45fd7158c32ae13b59cdca9386f34a985/R/block-ui.R#L188-L295)). Two mounts of one output share its parameters, which core keeps per block, so both show the same page and sort. A front-end shows a block's UI and its output as core's attribute `visible` says, which its toggles set where the board is not locked, since a locked board leaves open only the blocks whose inputs show ([Board objects](Rewrite-1.1.1#blocks), [Wire protocol](Rewrite-1.1.9#locked-boards)). The `mountOutput()` call measures its element for the output's `info`, asks R for the output unless core kept one asked with the same revision, board options, `info` and parameters ([UI modules in JS](Rewrite-1.1.7#the-contract)), draws it with the renderer R names in it (below), and redraws it when the block's revision, a board option, the `info` or the output's parameters change, while the block is `ready` ([Evaluation in the client](Rewrite-1.1.10#scheduling)). A front-end draws a block's status, conditions and summary from `scheduler.status()`, and decides from the status what an output that is not current looks like, leaving it as it is, greying it out or hiding it, since core keeps drawing a block's last output whatever the block's status ([Evaluation in the client](Rewrite-1.1.10#statuses)). It demands the blocks it shows, above the default evaluation priority ([Evaluation in the client](Rewrite-1.1.10#demand)), and follows the board through `store.subscribe()`, so a removed block's card goes away because the board changed, not because R said so. It draws no control for what the lock fixes ([Wire protocol](Rewrite-1.1.9#locked-boards)), and its extensions reach R through `request()`, each through requests of its own, as code export and session management do ([Wire protocol](Rewrite-1.1.9#requests)).

### Starting the page

Core starts the page in the order that [UI modules in JS](Rewrite-1.1.7#startup-modules) gives startup modules: once R replies to `hello`, core initializes the startup module of every package R has loaded, one at a time, then opens the board R sent, or the one a startup module names in its place (below), with the startup modules of any package that opening loads, then imports the module of the front-end that board names, since a module's imports run as it loads and may need what a startup module puts on the page, such as React ([UI modules in JS](Rewrite-1.1.7#react)), and only then starts the scheduler and calls the front-end's `render()`, so nothing is evaluated or drawn before every package has registered. The scheduler sends nothing to R until `render()` has returned, or resolved where it is async, so a front-end demands what it first shows within `render()`, from the board, rather than from an effect that runs once it has drawn, as a React app's would, and those blocks are evaluated first ([Evaluation in the client](Rewrite-1.1.10#scheduling)). A front-end's package registers what the front-end adds, such as the keys of the dock's state and its commands, from its startup module, and subscribes to the store there too, so that it sees the first board open, with what R dropped, which happens before `render()` ([Board updates](Rewrite-1.1.2#following-the-board)), while the front-end's module only draws.

A startup module's `initialize()` may resolve with the text of a saved file, as session management's does with the board a URL names ([Session management as a client extension](Rewrite-1.6)), and core then opens that board instead of the one R sent, except on a locked board, which loads no other board, where core keeps the board R sent and names the package ([Wire protocol](Rewrite-1.1.9#locked-boards)), so nothing of the script's board is drawn or evaluated, while the page shows that it is loading, as today's page waits for `rack_loader()` ([Defining a board in R](Rewrite-1.1.3#the-opening-board)). Should two resolve with a board, core opens the one R sent and names both packages.

### Switching front-ends

Opening a board whose `front_end.id` names another front-end than the page's switches the page to it, with no reload: once R has replied and the startup modules of the packages the opening loads have initialized ([UI modules in JS](Rewrite-1.1.7#startup-modules)), core imports the other front-end's module, aborts the signal of the one on the page, which unmounts what it mounted and releases its demands, opens the board in the store, and calls the new front-end's `render()`, holding the scheduler until it has returned, as at startup, so that what it first shows is evaluated first. Nothing else is lost, since opening a board starts a new undo history and has R forget every block whatever draws it ([Board updates](Rewrite-1.1.2#opening-a-board), [Wire protocol](Rewrite-1.1.9#forgetting-blocks)), and a front-end releases what it holds when its signal aborts, as any module does when core unmounts it ([UI modules in JS](Rewrite-1.1.7#the-contract)). So the page draws an opened board as a fresh app serving it would, as today's restore rebuilds the page for the restored board's class (Today) but without the reload: a core board opened in a dock app is drawn by core's basic front-end, and a dock board opened in a core app by the dock.

### Core's basic front-end

Core's own front-end does what today's does wherever core's commands and store do the work, so that it only draws: a toolbar for adding a block from the block registry's entries, editing links and stacks, setting the board's options and renaming the board, and downloading the board as a file and opening one, as today's `preserve_board` plugin does, since the client writes a saved board and opening one is `store.open()` ([Serialization](Rewrite-1.1.4#files)); stacks as groups; and a card per block with its name, a menu to rename or remove it or add a block before or after it, its UI, its output and its summary, as today's has, and its status and conditions, which today's computes but does not draw on the card, with the output greyed out while the block is not `ready`, where today's clears it ([R/block-server.R#L63-L66](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/block-server.R#L63-L66)). It also binds undo and redo to their shortcuts, the one thing today's lacks, since the store keeps the steps and a front-end binds the shortcuts ([Board updates](Rewrite-1.1.2#undo)), and it tells the user what R dropped when a board opened and which edit the store refused ([Board objects](Rewrite-1.1.1#objects-that-cannot-be-rebuilt)). Code export stays blockr.code's, to which [Client-drawn dock and extensions](Rewrite-1.2) gives today's `generate_code` plugin, and the basic front-end takes no extensions, since contribution points of its own would be a second extension API beside the dock's.

It shows every block, so it demands every block, and a board served without the dock evaluates every block ([Evaluation in the client](Rewrite-1.1.10#demand)), where today's parks the blocks of collapsed stacks. It is written in plain TypeScript, as core's built-in block UIs are, since core ships no React, and it mounts a block UI written in React as any front-end does, since the module brings its React from the one copy a package puts on the page ([UI modules in JS](Rewrite-1.1.7#react)). It follows blockr.ui's design system, as condition 6 of [State in JS](Rewrite-1#what-must-hold) asks of core's client, while where the design tokens live is an open question of [UI kit and design system for the client](Rewrite-1.7).

### Extensions

An extension is registered with the front-end it extends by its package's startup module ([UI modules in JS](Rewrite-1.1.7#startup-modules)), under an id, `{pkg}-{name}`, by which its package registers its requests in R and `request()` names them ([Wire protocol](Rewrite-1.1.9#requests)), while how a package declares an extension is [Client-drawn dock and extensions](Rewrite-1.2)'s, since only the dock takes extensions. It works on the board through the same `CoreApi`, so the DAG adds a link by running a command and draws its status badges from `scheduler.status()`, with no per-block callback. What it contributes to the screen goes through the front-end's contribution points, which for the dock are [Client-drawn dock and extensions](Rewrite-1.2)'s. Its state lives in the front-end's state, as keys it registers with the store through what its front-end offers, which the dock nests under `extensions` by the extension's id, and which other extensions and the assistant change as they change core's objects and which stay consistent through the `expand` each key registers ([Board updates](Rewrite-1.1.2#the-front-ends-state-and-attributes)). A file holds that state within the board and the version of the extension's package in its `packages`, while R reads the state a file from today's stack keeps next to the extension's constructor into the same keys ([Serialization](Rewrite-1.1.4#files)).

### Renderers

A renderer is a module that draws the outputs of one output class ([Block classes in R](Rewrite-1.1.5#outputs)) or a board option's value. A renderer of an output class is written against the class's contract, which the package that defines the class ships: a JSON Schema of its outputs, by which R writes them, with their TypeScript type, such as core's `TableOutput` for table outputs; the types of the parameters its coercion reads, such as `TableParams`, of the events its renderers emit, if they emit any, such as a chart's selection, and of the args and answers of its requests, if it has any, such as a download; and fixtures of sample outputs it is tested on, so that whoever builds another table knows what to draw and what to ask for. A package declares its renderers in R, as it declares a front-end, each for the one output class or board option it draws, with the board options it uses, as a block class names its own, and one module may stand behind several renderers: core declares a plain renderer for each output class it defines, such as `blockr.core-basic_table` for table outputs, blockr.ui declares its table preview, `blockr.ui-table_preview`, for the same class, and a front-end may declare renderers of its own, each with the id `{pkg}-{name}` that its package's name and the name it declares it under give. A renderer of an output class brings the board options the class's coercion reads in R too, such as `n_rows` for table outputs, naming the constructors of the package that defines the class, as both of today's table displays bring `n_rows` ([R/tabular-display.R#L141-L175](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/tabular-display.R#L141-L175)), so that R collects them whichever renderer it picks. R picks one renderer for each output class and each board option, the first of the one the `renderers` blockr option names for it by the renderer's id, the front-end's and another package's, and otherwise the renderer of the package that defines the class, while a board option keeps the `ui` its definition gives ([Board objects](Rewrite-1.1.1#options)). For each output, R names in its JSON the renderer it picked for the most specific class in the output's class vector that has one, as S3 dispatch would, so that the outputs of a subclass that no package draws are drawn by their class's renderer, and the client mounts the renderer an output names, so neither class vectors nor dispatch reach it ([State in JS](Rewrite-1#principles)). Another package thus replaces a class's renderer through R's pick, extends the class with a subclass, or nests the class's outputs in its own ([Block classes in R](Rewrite-1.1.5#outputs)). Two renderers at one step are an error naming both, which the app settles with the blockr option. R sends the client the renderers it picked with the block registry's entries, and collects the board options they bring as it collects a block class's ([Defining a board in R](Rewrite-1.1.3#options)). So an app, a front-end or a UI kit changes how every table looks without touching a block class, as a JupyterLab extension replaces the renderer of a MIME type by registering its own ([registry.ts#L232-L258](https://github.com/jupyterlab/jupyterlab/blob/a877aee5ac6f490272a5ac18ac16b62b0deb1223/packages/rendermime/src/registry.ts#L232-L258)):

```r
# blockr.core: its plain table, blockr.core-basic_table
register_renderer("basic_table", js_module("basic-table.js"), class = "table_output",
                  options = list(new_n_rows_option, new_page_size_option, new_filter_rows_option))

# blockr.ui: a richer table for every block whose output is a table, blockr.ui-table_preview
register_renderer("table_preview", js_module("table-preview.js"), class = "table_output",
                  options = list(new_n_rows_option, new_page_size_option))

# an app that wants core's plain table anyway: an output class, and the id of its renderer
options(blockr.renderers = c(table_output = "blockr.core-basic_table"))
```

A renderer gets an output host, or for a board option an option host ([UI modules in JS](Rewrite-1.1.7#the-contract)), through which it calls the requests of its output class, such as a download of what it shows, and draws an output nested in its own, such as the table in blockr.dm's view of a dm, with the renderer R names in the nested output. A block's UI has no renderer, since it ships the schema of its block's state ([Serialization](Rewrite-1.1.4#state-values-between-the-client-and-r)), so a different UI makes a block class of its own, built from the fields of the block's ([Block classes in R](Rewrite-1.1.5#cores-classes-and-hooks)).

### What goes from R

The generics that draw or redraw UI from R go: `board_ui()`, `block_ui()`, `insert_block_ui()`, `remove_block_ui()`, `toolbar_ui()`, the stack UI generics, `blockr_app_ui()` and `blockr_app_server()`, and so do the `callbacks` through which a front-end hooks into `board_server()`, which goes with the board server ([Client-owned board state](Rewrite-1.1#today)). A front-end's R side shrinks to declaring its front-ends with their modules, the board classes they draw and the board options they require (above), its startup module ([UI modules in JS](Rewrite-1.1.7#startup-modules)), any renderers of its own (above), the constructors that app scripts call, such as the dock's `new_dock_board()` and `new_dock_stack()`, whose state R writes as the front-end's state ([Board objects](Rewrite-1.1.1#extending-cores-objects)), and the blockr options its client reads ([Defining a board in R](Rewrite-1.1.3#blockr-options)).

### Testing

Core ships, beside the stubs of its hosts ([UI modules in JS](Rewrite-1.1.7#testing)), a `CoreApi` for tests whose store, commands and scheduler are core's own and whose replies from R come from fixtures, those the wire protocol's tests round-trip ([Wire protocol](Rewrite-1.1.9)), so that a front-end, an extension or a startup module runs in a test runner on a board, needing neither R nor a browser.
