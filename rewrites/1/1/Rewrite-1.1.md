# Client-owned board state
Status: implementing in [blockr#503](https://github.com/orgs/BristolMyersSquibb/discussions/503). Part of [State in JS](Rewrite-1).

This part covers blockr.core: the client's store, command registry and scheduler, the wire protocol and R's per-session evaluator, block classes and the modules that draw their UIs, opening, saving and serving a board, and core's basic front-end with the API every front-end draws on. Every other part builds on it, and its design pages set out each API.

## Problem

Of blockr.core's 18,353 lines of R, 7,405 hold the board and run it in the session's R process, on its one thread (Today, below): the board and block servers, which run board management, block construction, demand and visibility gating and every block's UI logic as Shiny reactives, the plugins, the lock and the generics that draw UI. Evaluation, the only part that needs R, waits behind all of it, and [State in JS](Rewrite-1#problem) sets out what that has led to.

## What must hold

Conditions 1 to 6 of [State in JS](Rewrite-1#what-must-hold) rest on this part, and so does this one:

1. A block's R side is plain functions: its expression from its state and data inputs, and what its UI needs from the same.
2. On a locked board, R evaluates only the opening board's blocks, with their opening links, and every block the app did not leave open with its opening state, whatever a client sends.

## Proposal

- The board is plain data held by a TypeScript store in core's JS API, in which the board names the front-end it is made for, each block names its class by registry id, and no object carries an R class ([Board objects](Rewrite-1.1.1)). Every edit, by the user, the assistant or an extension, is a delta in the `add`, `mod` and `rm` shape of today's `update()`, in which the assistant stages its edits already, and the same deltas give undo ([Board updates](Rewrite-1.1.2)).
- All edits run through one command registry, which menus, shortcuts, extensions and the assistant's tools call alike ([Board updates](Rewrite-1.1.2#commands)). It replaces the dock's action registry and core's plugins, since core keeps no plugin or extension type of its own ([State in JS](Rewrite-1#proposal)): a plugin's logic becomes commands and its UI a front-end's or an extension's, as [blockr.code#8](https://github.com/BristolMyersSquibb/blockr.code/issues/8) moves code export into a dock extension.
- An app is still an R script that calls `serve()` on a board built with constructors, and that board becomes the client's opening board ([Defining a board in R](Rewrite-1.1.3)). The client opens every board, at startup or from a file, itself, migrating what older versions of its packages saved in JS and dropping what the app cannot rebuild, while R only loads the packages the board names and registers their block classes, and replies with the block registry's entries, which replace the client's ([Board updates](Rewrite-1.1.2#opening-a-board)), as it does for the packages of the board a client holds when it starts a new session ([Wire protocol](Rewrite-1.1.9#handshake)). Saving and restoring needed core today, since a restore is a `session$reload()` that the app's `board_loader()` handles ([R/utils-serve.R#L277-L288](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L277-L288)); here the store opens a board in place of the one it holds, which is all session management needs. The client writes a saved board as the board itself, with the versions of its packages ([Serialization](Rewrite-1.1.4)), and core's basic front-end saves one only as a download, while where else it is saved, such as to Connect or a draft, is session management's, built on the store and on requests its package adds ([Session management as a client extension](Rewrite-1.6)).
- R is an evaluator, one process per session, holding results and no board state. An evaluation request carries the recipe, a block's registry id and state with its inputs as upstream block ids and revisions, and R builds the block expression from its class's `expr` and runs it with `block_eval()`, keeping the latest result by block id and revision, never by process, so a client that starts a new session with its board loses only recomputation ([Wire protocol](Rewrite-1.1.9#evaluating-a-block)). A block class is a value defined once, from which its constructor is made, and R calls a constructor only where a board is built ([Block classes in R](Rewrite-1.1.5)). A result is any R object, which the coercion its block class names turns into an output, so nothing in the protocol assumes a table, drawn by the renderer the app picks for the output's class, which a front-end or a UI kit replaces without touching a block class ([Front-ends and extension points](Rewrite-1.1.8#renderers)). A reply carries the block's status, block expression and conditions, and the client decides which to show, so `show_conditions` stays a board option of core's, which a front-end reads to choose the severities it shows, while R reports every severity.
- The client schedules. It bumps a block's revision on every change to its recipe, its state or the links into it, or to anything upstream of it, the way spreadsheets and notebooks track their cells, keeps the last results on screen, and evaluates what is demanded, and everything upstream of it, by the evaluation priority each demand gives and in topological order within one, which replaces construction ordering, the render gate and the visibility channels in R ([Evaluation in the client](Rewrite-1.1.10)). Board options never reach `expr`: one that shapes outputs redraws them without re-evaluating, and a block that reads relative to a directory takes the directory as an input. What is demanded is what the front-end shows, every block under core's basic front-end, together with what extensions and packages demand, such as blockr.io for a write block in auto mode ([Evaluation in the client](Rewrite-1.1.10#demand)).
- A block's UI is an ES module that core mounts with an injected host, under a contract free of any framework ([UI modules in JS](Rewrite-1.1.7)). Core ships no React: its built-in blocks and board options write their UIs in plain TypeScript, and a block package that writes its UI in React, as TSX the way an app writes a `ui.tsx` in shinyreact's pattern ([README.md#L18-L22](https://github.com/posit-dev/shinyreact/blob/e8812353d5f076f6e98a27a7e210d0a3e177ea1d/README.md#L18-L22)), builds it with `react` mapped to the one copy that a package puts on the page from its startup module ([UI modules in JS](Rewrite-1.1.7#react)). Core loads JS only, so every package's JS ships inside its R package, built by the package where it is written in TSX, and nothing goes to npm for now. Core treats the UI as a black box ([State in JS](Rewrite-1#principles)), so input elements composed in R leave core, and ready-made components for form-like UIs may come later from blockr.ui. The JSON a module exchanges with R is private to its block class, and the arg specs describe args for LLMs and tools, while a block's UI decides their shapes and ships their schema ([Serialization](Rewrite-1.1.4#state-values-between-the-client-and-r)).
- Core ships a basic front-end that draws any board, so a board serves without blockr.dock, and a front-end such as the dock replaces it for the boards made for it. A front-end draws everything around a block and works on the board through `CoreApi`, while core mounts the block's UI and output, so a block class works in every front-end and nothing in R draws UI ([Front-ends and extension points](Rewrite-1.1.8)).
- Core has a JS API and an R API, with a versioned wire protocol between them that both sides test against shared fixtures, as shinyreact does ([Wire protocol](Rewrite-1.1.9)). R builds every block's expression from its class's `expr`, so the code a block shows and exports is the code that ran. R decodes what the client sends into plain values, never code ([Wire protocol](Rewrite-1.1.9#decoding)), but a block may parse a string into code, so a board can run any R code, and limiting what the R process may do is the deployment's job, such as a sandbox around it. So is access: core knows nothing about users, since access is the data source's, through the process's file permissions or an API client's own token, and results are never shared between sessions, since what a read returns can depend on who runs it.
- An app locks a board when it starts, and R holds the lock in what it runs, so no client can loosen it: the board loads no other board, its blocks, links, stacks and board options are fixed, and so is the state of every block the app does not leave open, since R takes every block's class and input bindings, and a locked block's whole block expression, from what it builds when the app starts ([Wire protocol](Rewrite-1.1.9#locked-boards)). A front-end may lock more of what it alone governs, as the dock does the arrangement of its panels.
- Other requests belong to an object too, as a block's belong to its class: to an output class, for what its renderers offer beyond the output, such as a download of what they show, to a board option, as blockr.io's data directory lists the server's directories, or to an extension, for work that belongs to no single block and needs R or the server, such as code generation in blockr.code, or exchanging a visitor's Connect session token, which only the content's process receives, for the key that session management's storage calls then use from the browser ([Session management as a client extension](Rewrite-1.6)). A block class's request reads the block's inputs at given revisions, with the state args, board options and parameters it names, so the client caches its answers by them unless the class marks the request volatile or an action, which may write. An output class's request reads the result its output was made from, with the board options and parameters that output was asked with, and is cached as the output is, while a board option's or an extension's request may write and is never cached ([Wire protocol](Rewrite-1.1.9#requests)). There is no generic request for a column's values: a value list is a block class's own request, bounded by its author. Effects need no mechanism of their own: a write is a block expression, which a write block's `block_eval()` method runs in auto mode, and in manual mode only when its save button asks, through a one-time evaluation with a parameter ([Block classes in R](Rewrite-1.1.5#evaluation)), an upload is a request its class marks as an action, which runs once per call and may write, and a download is a request whose answer is a file with its name ([UI modules in JS](Rewrite-1.1.7#the-contract)).
- Shiny stays as host and transport for now, since on Connect a Shiny app with *Max connections per process* at 1 gives each session its own process. A small bridge module carries the protocol ([Wire protocol](Rewrite-1.1.9#the-shiny-bridge)), rather than shinyreact, whose API is React hooks and components and has no request and response, and leaving Shiny later replaces that module.
