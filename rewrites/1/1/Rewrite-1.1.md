# Client-owned board state
Status: review. Part of [State in JS](Rewrite-1).

This part covers blockr.core: the client's store, command registry and scheduler, the wire protocol and R's per-session evaluator, block types and the modules that draw their UIs, opening, saving and serving a board, and core's basic front-end with the API every front-end draws on. Every other part builds on it, and its design pages set out each API.

## Problem

Of blockr.core's 18,353 lines of R, 7,405 hold the board and run it in the session's R process, on its one thread (Today, below): the board and block servers, which run board management, block construction, demand and visibility gating and every block's UI logic as Shiny reactives, the plugins, the lock and the generics that draw UI. Evaluation, the only part that needs R, waits behind all of it, and [State in JS](Rewrite-1#problem) sets out what that has led to.

## What must hold

Conditions 1 to 6 of [State in JS](Rewrite-1#what-must-hold) rest on this part, and so does this one:

1. A block's R side is plain functions: its expression from its state and data inputs, and what its UI needs from the same.
2. On a locked board, R evaluates only the opening board's blocks, with every state arg the app did not leave open at its opening value, whatever a client sends.

## Proposal

- The board is a document of plain data held by a TypeScript store in core's JS API, in which the board and each block name their types by registry id and no object carries an R class ([Document model](Rewrite-1.1.1)). Every edit, by the user, the assistant or an extension, is a delta in the `add`, `mod` and `rm` shape of today's `update()`, in which the assistant stages its edits already, and the same deltas give undo ([Board updates](Rewrite-1.1.2)).
- All edits run through one command registry, which menus, shortcuts, extensions and the assistant's tools call alike ([Board updates](Rewrite-1.1.2#commands)). It replaces the dock's action registry and core's plugins, since core keeps no plugin or extension type of its own ([State in JS](Rewrite-1#proposal)): a plugin's logic becomes commands and its UI a front-end's or an extension's, as [blockr.code#8](https://github.com/BristolMyersSquibb/blockr.code/issues/8) moves code export into a dock extension.
- An app is still an R script that calls `serve()` on a board built with constructors, and that board becomes the client's opening document ([Defining a board in R](Rewrite-1.1.3)). Opening a board, at startup, from a file or after R restarts, goes through R, which loads the packages and registers the block types the board names, migrates its blocks and replies with the document and the registry, which replace the client's ([Board updates](Rewrite-1.1.2#opening-a-board)). Saving and restoring needed core today, since a restore is a `session$reload()` that the app's `board_loader()` handles ([R/utils-serve.R#L277-L288](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L277-L288)); here the store opens a board in place of its document, which is all session management needs. The client writes a saved board, in the shape `blockr_ser()` writes today ([Serialization](Rewrite-1.1.4)), and where it is saved is session management's, built on the store and on requests its package adds ([Session management as a client extension](Rewrite-1.6)).
- R is an evaluator, one process per session, holding results and no board state. A request carries the recipe, a block's registry id and state with its inputs as upstream block ids and versions, and R evaluates it with the block type's `validate`, `interpolate` and `evaluate`, keeping the latest result by block id and version, never by process, so a lost process costs only recomputation ([Wire protocol](Rewrite-1.1.9#evaluating-a-block)). A block type is a value defined once, from which its constructor is made, and R calls a constructor only where a board is built ([Block types in R](Rewrite-1.1.5)). A result is any R object, shown through its type's `output`, so nothing in the protocol assumes a table. A reply carries the block's status, expression and conditions, and the client decides which to show, so `show_conditions` becomes a display setting.
- The client schedules. It bumps a block's version on every change to the block or to anything upstream of it, the way spreadsheets and notebooks track their cells, keeps the last results on screen, and evaluates what is demanded, and everything upstream of it, in topological order, which replaces construction ordering, the render gate and the visibility channels in R ([Evaluation in the client](Rewrite-1.1.10)). Board options never reach `interpolate`: one that shapes outputs redraws them without re-evaluating, the `evaluation` option decides what the client demands, and a block that reads relative to a directory takes the directory as an input.
- A block's UI is an ES module that core mounts with an injected host, under a contract free of any framework ([UI modules in JS](Rewrite-1.1.7)). Core ships no React: its built-in blocks and options write their UIs in plain TypeScript, and a block package that writes its UI in React, as TSX the way an app writes a `ui.tsx` in shinyreact's pattern ([README.md#L18-L22](https://github.com/posit-dev/shinyreact/blob/e8812353d5f076f6e98a27a7e210d0a3e177ea1d/README.md#L18-L22)), gets React and the React SDK from blockr.ui, which ships the one copy the dock uses too ([UI kit and design system for the client](Rewrite-1.7)). How TSX is built is still to be worked out, but every package's JS ships inside its R package, and nothing goes to npm for now. Core treats the UI as a black box ([State in JS](Rewrite-1#principles)), so input elements composed in R leave core, and ready-made components for form-like UIs may come later from blockr.ui. The JSON a module exchanges with R is private to its block type, and the arg specs describe args for LLMs and tools and are not checked at run time, since a block's UI decides their shapes.
- Core ships a basic front-end that draws any board, so a board serves without blockr.dock, and a front-end such as the dock replaces it by registering for a board type. A front-end draws everything around a block and works on the board through `CoreApi`, while core mounts the block's UI and output, so a block type works in every front-end and nothing in R draws UI ([Front-ends and extension points](Rewrite-1.1.8)).
- Core has a JS API and an R API, with a versioned wire protocol between them that both sides test against shared fixtures, as shinyreact does ([Wire protocol](Rewrite-1.1.9)). R builds every expression with the block type's `interpolate`, so the code a block shows and exports is the code that ran. R decodes what the client sends into plain values, never code ([Wire protocol](Rewrite-1.1.9#decoding)), but a block may parse a string into code, and opening a board may evaluate the definition of a block type defined outside a package where the `load_definitions` option allows it ([Document model](Rewrite-1.1.1#block-types-outside-a-package)), so a board can run any R code, and limiting what the R process may do is the deployment's job, such as a sandbox around it. So is access: core knows nothing about users, since access is the data source's, through the process's file permissions or an API client's own token, and results are never shared between sessions, since what a read returns can depend on who runs it.
- An app locks a board when it starts, and R holds the lock in every recipe, so no client can loosen it: the board's blocks, links, stacks and options are fixed, and so is every state arg the app does not leave open, while R evaluates only the opening board's blocks and opens no other board ([Wire protocol](Rewrite-1.1.9#locked-boards)). A front-end may lock more of what it alone governs, as the dock does the arrangement of its panels.
- Other requests are registered per block type, or per package for work that belongs to no single block and needs R or the server, such as code generation in blockr.code, or exchanging a visitor's Connect session token, which only the content's process receives, for the key that session management's storage calls then use from the browser ([Session management as a client extension](Rewrite-1.6)). A block type's request reads the block's inputs or its result at given versions and never reads block state implicitly, so the client caches its answers, while a package's request may write and is never cached ([Wire protocol](Rewrite-1.1.9#requests)). There is no generic request for a column's values: a value list is a block type's own request, bounded by its author. Effects need no mechanism of their own: a write is a block's expression, a manual save a click that bumps its state, a download a result whose output hands the file over, and an upload a request carrying the file.
- Shiny stays as host and transport for now, since on Connect a Shiny app with *Max connections per process* at 1 gives each session its own process. A small bridge module carries the protocol ([Wire protocol](Rewrite-1.1.9#the-shiny-bridge)), rather than shinyreact, whose API is React hooks and components and has no request and response, and leaving Shiny later replaces that module.

## Open questions

- The questions of the design pages that change what an issue asks, and so settle before the issues open: which JSON decoding R applies ([Wire protocol](Rewrite-1.1.9#open-questions)), how an app names what its lock leaves open, and whether an arg that becomes code may be left open ([Wire protocol](Rewrite-1.1.9#open-questions)), whether `serve()` keeps a loader that replaces the opening board for a session, how a data block names data that R keeps, and where configuration that a constructor takes goes ([Defining a board in R](Rewrite-1.1.3#open-questions)), where the card's summary comes from ([Block types in R](Rewrite-1.1.5#open-questions)), how a block type's TSX is built and whether a custom element is a second form of the module contract ([UI modules in JS](Rewrite-1.1.7#open-questions)), and what core's basic front-end offers ([Front-ends and extension points](Rewrite-1.1.8#open-questions)). Their other questions can be settled in the issues, by building or measuring.
