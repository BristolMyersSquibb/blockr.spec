# Evaluation in the client: revisions, demand and statuses
Status: review. Design for [Client-owned board state](Rewrite-1.1).

One of the API proposals for the client-owned board ([Client-owned board state](Rewrite-1.1)): what the client tracks about evaluation, and the API front-ends and extensions use to ask for it. It builds on the [board objects](Rewrite-1.1.1), [board updates](Rewrite-1.1.2) and [wire protocol](Rewrite-1.1.9) proposals, and shapes building the client scheduler, an item in the Work list of [Client-owned board state](Rewrite-1.1#work). The messages that carry an evaluation are the wire protocol's, a front-end demands the blocks it shows as [Front-ends and extension points](Rewrite-1.1.8#what-core-gives-a-front-end) has it, and core fetches and draws a block's output as [UI modules in JS](Rewrite-1.1.7#the-contract) has it. It moves into the client the demand and statuses that today's board server has from [blockr#489](https://github.com/orgs/BristolMyersSquibb/discussions/489) and [blockr#488](https://github.com/orgs/BristolMyersSquibb/discussions/488), and keeps the statuses' names.

## What must hold

1. A board evaluates what its front-end shows, every block under core's basic front-end and what is on screen under the dock, as boards do today.
2. A board edit costs no R time beyond evaluating what is demanded and fetching outputs for what is on screen, except what an app has R evaluate in the background, which starts only while R has nothing else to run.
3. Any front-end, extension or package can demand a block or invalidate one without knowing who else does, and without saying why.
4. A block's status, conditions, block expression and summary read the same whether or not it is demanded, as they do on today's board ([blockr#488](https://github.com/orgs/BristolMyersSquibb/discussions/488)), so whatever reads neither `stale` nor `unevaluated` holds for the block's current revision.
5. A block that must run with nothing on screen, such as a write block in auto mode, runs whatever the front-end shows, and a component that needs current results, such as the code export, gets them without putting a block on screen.
6. At startup, the blocks the front-end shows and everything upstream of them are evaluated before any other block, so that first paint waits for no block off screen, as today's core builds their servers first ([blockr.core#243](https://github.com/BristolMyersSquibb/blockr.core/issues/243)).

## Today

Today's board server gives every block one of the statuses of [blockr#488](https://github.com/orgs/BristolMyersSquibb/discussions/488), `unevaluated`, `stale`, `waiting`, `unset`, `failed` or `ready`, and a block nothing needs keeps what its last check found, which reads `stale` once anything the check read has changed ([R/block-server.R#L20-L71](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/block-server.R#L20-L71)). A block is needed while an owner holds it eager or it feeds one that is: a front-end makes the board lazy by returning `eager()` with the blocks it shows from the callback it registers, any other owner holds blocks through the `eager` component of a board update or brings them up to date once through its `evaluate` component, and the `gate_visibility` blockr option, set to `FALSE`, keeps every board eager ([R/block-server.R#L79-L105](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/block-server.R#L79-L105), [R/board-server.R#L21-L78](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/board-server.R#L21-L78)). The servers of blocks nothing needs are built in the background once the front-end has painted what it holds eager, and evaluate nothing ([R/block-server.R#L113-L123](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/block-server.R#L113-L123), [#L402-L404](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/block-server.R#L402-L404)).

## Proposal

### Revisions

Every block has a revision, a number the client keeps for the page and never saves, since a board that opens meets an R process that holds no result of it. A block's revision goes up whenever its recipe changes ([Wire protocol](Rewrite-1.1.9#evaluating-a-block)): its state, the links into it, other than in their names, and the revision of any block upstream of it, so a change reaches everything downstream. It also goes up when something invalidates the block (below). Nothing else changes a revision: not renaming a block or a link, changing a block's attributes or moving it between stacks, nor changing a field or a board option, which never reaches `expr` and redraws outputs without evaluating ([Client-owned board state](Rewrite-1.1#proposal)). Within the page a block id's revision never goes back: the scheduler forgets a block's status when R forgets its result, as when the block leaves the board or another board opens ([Wire protocol](Rewrite-1.1.9#forgetting-blocks)), and a block that comes back, by undo or in the board that opens, takes a revision above any its id had and reads `unevaluated` until its first reply, so that a late reply never passes for a newer revision. A block is stale while its revision is newer than the revision of its latest reply. The revision is the scheduler's, apart from the edit id the store keeps for each block, which only the block's own edits change ([Board updates](Rewrite-1.1.2#deltas)).

### Demand

The scheduler keeps every block that something demands evaluated, together with everything upstream of it, and evaluates nothing else, but for one-time evaluations and, where an app turns it on, evaluation in the background (below). A demand has an owner, and every owner demands the same way, so core never learns why a block is demanded, as [blockr#489](https://github.com/orgs/BristolMyersSquibb/discussions/489) has it for the R board:

- A demand is a set of blocks, such as what the dock shows, or a function of the board, which the scheduler calls again after every change to the board, such as blockr.io's demand for every write block whose `auto_write` is on. The handle that `demand()` returns replaces or releases it, so an owner may hold several and none replaces another's, while the owner's name says whose a demand is, so that core can name it, as when a function of the board throws (notes). A function of the board is how a block keeps evaluating with nothing on screen, by its own state or by any setting the board holds, so a block class declares nothing about it ([Block classes in R](Rewrite-1.1.5#the-block-class)), and a front-end or an extension can let the user keep any block evaluated through a field it keeps and a function that reads it ([Board updates](Rewrite-1.1.2#fields)).
- A front-end demands the blocks it shows ([Front-ends and extension points](Rewrite-1.1.8#what-core-gives-a-front-end)): the dock what is on screen, and core's basic front-end every block, since it shows every block. The `gate_visibility` blockr option, `TRUE` by default as today, has core demand every block when set to `FALSE`, whatever the front-end shows, for an app that wants every result current.
- A one-time evaluation brings some blocks and their upstream up to date without keeping them so: it evaluates those that read `stale` or `unevaluated`, and resolves with their statuses once none of them does, at whatever revision each has by then, so that an edit made while it waits delays it, rather than leaving it waiting for a revision whose reply the scheduler drops. It resolves with each block's status by its id, leaves out a block that leaves the board meanwhile, and rejects once it is left with none or when another board opens, as a host's `submit()` and `evaluate()` do ([UI modules in JS](Rewrite-1.1.7#the-contract)), and stops once its caller aborts the signal it may pass, such as for an assistant's step that was given up. The code export and the assistant run one ([Code export as a client extension](Rewrite-1.5), [Assistant as a client extension](Rewrite-1.4)), and a request that reads blocks, a block class's or a package's, has them evaluated this way before it runs, and goes to R, at the revisions they then have, only where each reads `ready`, rejecting otherwise with their statuses, so that R never runs a request on a result it does not hold ([UI modules in JS](Rewrite-1.1.7#the-contract), [Wire protocol](Rewrite-1.1.9#requests)).
- A one-time evaluation can carry parameters, which R passes to the `block_eval()` method of each block it names, and then evaluates those blocks whether they are stale or not, as a write block's save button does ([UI modules in JS](Rewrite-1.1.7#the-contract), [Block classes in R](Rewrite-1.1.5#evaluation)). It is its caller's one call for what such a method does, such as a write, which nothing would make again, so it runs once, as an action does: the scheduler sends it, once what the blocks read upstream is evaluated, for the revisions the blocks have when it is called, sends no other evaluation of those revisions, never cancels it, whatever its evaluation priority, and resolves with the statuses its replies give for those revisions, which become the blocks' own where those revisions are still current. It rejects where its block leaves the board before it is sent, and where a new session starts before it is answered, since it may have run (Scheduling).

Every demand and one-time evaluation has an evaluation priority, a number that defaults to 0, and a block takes the highest of anything that needs it, itself or a block downstream of it, so that what a view shows and everything upstream of it go first. A front-end demands what it shows above the default, as today's core re-prioritizes construction toward the view that navigation brings on screen ([blockr.core#275](https://github.com/BristolMyersSquibb/blockr.core/issues/275)), and one that shows every block, as core's basic front-end does, may demand what is in view higher still. An evaluation priority says how soon an owner needs its blocks, never why: it orders evaluations, and one below 0 gives way to whatever waits behind it (Scheduling), as evaluation in the background does at -1, which alone also waits for R to be idle. Both `demand()` and `evaluate()` take it as their `priority` option, after a demand's blocks and a one-time evaluation's parameters, and a request has the blocks it reads evaluated at the default, after what the front-end shows.

An app can also have R evaluate in the background the stale and unevaluated blocks nothing demands, with the `background_evaluation_delay` blockr option: once R has had nothing else to run for that many seconds, no evaluation at 0 or above, no output and no request, the scheduler evaluates them at evaluation priority -1, one at a time, until any of those arrives, as the blockx prototype at cynkra evaluates the rest of the board after the view on screen ([blockr.core#395](https://github.com/BristolMyersSquibb/blockr.core/issues/395)). Its default, `Inf`, evaluates nothing in the background, as today's background pass builds block servers but evaluates none, and the option takes over the role of today's `background_construction_delay`, which goes with the block servers, in seconds of idle time rather than milliseconds between two blocks. Sending one at a time keeps what anything else can wait behind to the one background evaluation R has started, for as long as it runs, or 5 s where R stops it (below).

```ts
const shown = scheduler.demand("blockr.dock", ["a", "b"], { priority: 1 });   // a set: what the dock shows, ahead of the default
shown.set(["a", "c"]);                                                         // replaced as the view changes
shown.release();

scheduler.demand("blockr.io", board =>                                         // a function of the board, called after every change
  Object.keys(board.blocks).filter(id =>
    board.blocks[id].registry_id === "blockr.io-write_block" && board.blocks[id].state.auto_write === true));

const statuses = await scheduler.evaluate(["b", "c"]);                         // a one-time evaluation, resolving with their statuses
await scheduler.evaluate(["w"], { save: true });                               // with parameters, which run w even where it is not stale
```

### Invalidation

```ts
scheduler.invalidate("a");   // bumps a and everything downstream
```

Any front-end, extension or package may invalidate a block, such as the user from a block's menu, which a front-end draws and which invalidates through `CoreApi`, or an extension, so a block that reads something outside the board, such as a file that changed on disk, runs again when asked to ([UI modules in JS](Rewrite-1.1.7#the-contract)). Invalidating changes no state, so it is no delta, which nothing undoes or saves, and a block nothing demands only turns `stale`.

### Statuses

```ts
type Status = "unevaluated" | "stale" | "waiting" | "invalid" | "ready" | "failed";

interface BlockStatus {
  status: Status;
  revision: number;                                // the block's current revision
  evaluated: number | null;                        // the revision its latest reply was for
  running: boolean;                                // whether an evaluation of it is sent and not yet answered
  conditions: Condition[];                         // from the latest reply, which replaces the ones before
  omitted: { warning: number; message: number };   // the conditions that reply counted rather than kept
  stdout: string;                                  // its standard output and error, bounded
  stderr: string;
  expr: string | null;                             // the block expression R built for that revision
  summary: string | null;                          // the result's summary from that reply, "<data.frame> [150 × 7]"
}

scheduler.status("b");                                         // the block's status now, read by whatever draws it
scheduler.subscribe(changed => { /* redraw these blocks */ });  // after statuses change, naming the blocks whose status changed
```

The names are today's ([R/block-server.R#L20-L71](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/block-server.R#L20-L71)), with `invalid` in place of `unset`, since a block class says only whether a state can run, by signalling `invalid()` in its `expr` or its `block_eval()` method or using an arg the state leaves unset ([Block classes in R](Rewrite-1.1.5#expressions)), and the conditions are those a reply carries ([Wire protocol](Rewrite-1.1.9#evaluating-a-block)). A block's status is the first of these that holds:

1. It is `waiting` while an input without a default is unlinked and R does not bind it itself, as it binds the data `serve()` is given for a block it serves alone ([Defining a board in R](Rewrite-1.1.3#data-passed-to-serve)), while a variadic block has no link, or while a block upstream reads `failed`, `invalid` or `waiting`, which the client sees from the block registry, the board and the reply to `hello` without asking R ([Block classes in R](Rewrite-1.1.5#the-block-class), [Wire protocol](Rewrite-1.1.9#handshake)).
2. It is `unevaluated` before its first reply.
3. It is `stale` while its revision is newer than its latest reply's, whether anything demands it or not.
4. It is what that reply says: `ready` for `ok`, `failed` for `error` and `invalid` for `invalid`.

A reply of `cancelled` or `missing` counts as none, since the scheduler sends again what it still needs, where a `missing` has it evaluate again a block R names whose current revision reads `ready`, and so had a result that R has lost, never one that reads `failed` or `invalid`, which had none. A block nothing demands reads the same way, so one that failed and has not changed since still reads `failed`, and a `stale` block keeps its latest reply's conditions, so one that failed before it went stale shows why. The conditions of an `invalid` reply hold the message of its `invalid()` or name the unset arg. While a block is `waiting`, its status holds no block expression or summary, and as its conditions only one the scheduler writes, of the phase `status`, naming the unlinked input or the upstream block that keeps it waiting, as today's board server records a note for `waiting` and `unset` with no result ([R/block-server.R#L66-L71](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/block-server.R#L66-L71)).

### Scheduling

After every change to the board, to a demand or to a revision, and after every reply, the scheduler works out what is demanded and what feeds it, and queues the blocks among them that read `stale` or `unevaluated`, highest evaluation priority first and in topological order within one. It holds what is still to send itself and sends R only a few evaluations ahead of the one R runs, which R runs one at a time in the order they arrive, making an evaluation wait for an input still computing ([Wire protocol](Rewrite-1.1.9#one-request-at-a-time)), so that a new evaluation priority or revision takes effect at the next send, nothing superseded waits in R beyond those few, and the protocol needs no message to reorder what R holds, as the `prio` message of the blockx prototype at cynkra does ([blockr.core#393](https://github.com/BristolMyersSquibb/blockr.core/issues/393)). When a block's revision changes while R holds its evaluation, the scheduler cancels the evaluation, unless it carries parameters (above), and never lets its reply set the block's status, as it ignores the reply for a block that reads `waiting` by the time it arrives, such as one whose upstream failed meanwhile. It also cancels an evaluation R has not started that nothing needs any more, as after a view switch, and one below evaluation priority 0 once anything else, an evaluation at a higher one, an output or a request, has waited 5 s behind it, which it queues again once R replies `cancelled`, so that evaluation in the background, for now the only one below 0, never holds up for long what someone asked for. Whether a cancel stops what R has started is R's to say ([Wire protocol](Rewrite-1.1.9#cancelling)): an evaluation R runs to its end replies as it would have, and the scheduler takes that reply as any other. It cancels nothing at 0 or above to make way for anything, since a demanded evaluation that gave way to every edit on screen, such as a write block's in auto mode, might never finish.

At startup the scheduler sends nothing until the front-end's `render()` has returned, or resolved where it is async, and the front-end demands what it first shows before then, from the board, rather than from an effect that runs once it has drawn, as a React app's would, so that those blocks and everything upstream of them are evaluated first ([Front-ends and extension points](Rewrite-1.1.8#starting-the-page)), as today's core seeds the front-end's opening demand before the first flush ([R/block-server.R#L79-L95](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/block-server.R#L79-L95)). A block that `serve()` serves alone has no front-end, so core's client, which draws it, demands it as a front-end would, and the scheduler starts once core has mounted it ([Defining a board in R](Rewrite-1.1.3#data-passed-to-serve)). Outputs are fetched by whatever draws them, once a block is `ready`, and core keeps drawing a block's last output whatever its status, so that the front-end decides from the status what an output that is not current looks like ([Front-ends and extension points](Rewrite-1.1.8#what-core-gives-a-front-end)), while it asks R for no other output of a block that is not `ready`, even when a board option or the element's size changes, since R may no longer hold the revision that output was made from.

After the `hello` of a new session, which holds no results, the scheduler takes every block's result as lost while keeping its status, evaluates again what is demanded and what a one-time evaluation still waits for, with everything upstream, and sends again every request of a block class still unanswered, while front-ends keep drawing the last outputs core holds ([Wire protocol](Rewrite-1.1.9#evaluating-a-block)). A one-time evaluation with parameters, an action and a package's request still unanswered reject instead, since they may have run and may write.

There is no early cutoff: a recomputed R result is a new object, so an identity check would not fire, and hashing results costs time in proportion to their size. Cutoff can come later, opt-in per block class.

## Open questions

- How many evaluations the scheduler keeps R ahead of the one it runs, which only measuring settles, in the scheduler's issue: the fewest with which R does not wait between evaluations on the CEDX board over a link with a 40 ms round trip, the link the blockx prototype was measured on ([blockr.core#395](https://github.com/BristolMyersSquibb/blockr.core/issues/395)).

<details><summary>Notes for implementers</summary>

A set may name blocks that are no longer on the board, which the scheduler passes over, so a block that undo brings back is demanded again by any set that still names it. A function of the board that throws demands nothing until it next returns, and the scheduler names its owner in an error, as core names a startup module that throws ([UI modules in JS](Rewrite-1.1.7#startup-modules)). The scheduler works out what to send once the task in which the board changed has ended, after every subscriber of the store has been told of the change, so that a front-end that changes its demand from its own subscription, as on an opening, is heard first.

The precedents, Excel's recalculation of every dependent of changed data, the counter Observable's runtime keeps per variable and Incremental's bringing up to date only what leads to an observed node, are on [blockr.core#395](https://github.com/BristolMyersSquibb/blockr.core/issues/395), whose comment gives what the blockx prototype at cynkra measured when it sent rows only for the blocks on screen.
