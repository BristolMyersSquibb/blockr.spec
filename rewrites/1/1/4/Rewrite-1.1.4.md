# Serialization of the client-owned board
Status: settled on 2026-10-28. Design for [Client-owned board state](Rewrite-1.1).

One of the API proposals for the client-owned board ([Client-owned board state](Rewrite-1.1)): how a board is written to a file and read back, and how state values travel between the client and R. It builds on the [board objects proposal](Rewrite-1.1.1), which says what the board holds, and shapes the JSON decoding of the wire protocol document ([blockr.core#420](https://github.com/BristolMyersSquibb/blockr.core/issues/420)), exporting the block registry ([blockr.core#426](https://github.com/BristolMyersSquibb/blockr.core/issues/426)), writing a board's JSON in R by schema ([blockr.core#428](https://github.com/BristolMyersSquibb/blockr.core/issues/428)), loading the packages that a board names in R ([blockr.core#429](https://github.com/BristolMyersSquibb/blockr.core/issues/429)) and writing saved boards in the client ([blockr.core#436](https://github.com/BristolMyersSquibb/blockr.core/issues/436)), each an item in the Work list of [Client-owned board state](Rewrite-1.1#work). How the client opens a board is the [board updates proposal](Rewrite-1.1.2#opening-a-board), and where a board is saved, to Connect or a draft, is session management's ([Session management as a client extension](Rewrite-1.6)), beside the download that core's basic front-end offers ([Front-ends and extension points](Rewrite-1.1.8#cores-basic-front-end)): core owns what a saved board is, and saves one itself only as a download.

## What must hold

1. Boards written by today's `blockr_ser()` open in the new stack, with the dock's views and layouts and the DAG's positions, for block classes that have been ported, as condition 4 of [State in JS](Rewrite-1#what-must-hold) asks: converted to saved files once, outside core, their blocks through `blockr_deser()` and the migrations packages already have, after which the client opens them as any saved file, the front-end's state through the migrations of the packages it comes from, in JS.
2. A board saved by the new stack is written in the browser, so saving needs no R and works while R is busy or gone.
3. The client's board holds state values its UI can use as they are, so an arg that is a vector is always an array, whatever its length.
4. A file written by the new stack is the board as the client holds it, with only what opening it needs beside it, and names no R class or constructor, while a file of today's stack is converted to one outside core.
5. Reading a file runs no code from it, as condition 3 of [Wire protocol](Rewrite-1.1.9#what-must-hold) asks of everything the client sends.

## Today

The `blockr_ser()` function returns R lists, and the JSON is up to the caller. Core's own download and upload write them with typedjson ([R/plugin-serdes.R#L76-L78](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/plugin-serdes.R#L76-L78), [#L179-L181](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/plugin-serdes.R#L179-L181)), which writes a length-one vector bare ([format](https://github.com/nbenn/typedjson/blob/371144d1170eb738395e85c875c368fe8e787b43/README.md)), while blockr.session writes with `jsonlite::write_json()`, which keeps it in an array, and reads with `jsonlite::fromJSON()`, simplifying neither data frames nor matrices ([R/rack.R#L249-L254](https://github.com/BristolMyersSquibb/blockr.session/blob/5f9b8e6aff54a58f84d2658963194c60e8a4262a/R/rack.R#L249-L254), [#L469-L473](https://github.com/BristolMyersSquibb/blockr.session/blob/5f9b8e6aff54a58f84d2658963194c60e8a4262a/R/rack.R#L469-L473)). A one-block stack therefore comes out as `"blocks": "a"` in one file and `"blocks": ["a"]` in the other, and JSON written with length-one vectors bare is what broke the dock's layout restore in [blockr.dock#91](https://github.com/BristolMyersSquibb/blockr.dock/issues/91).

## Proposal

### Files

A file written by the new stack is the board as the client holds it ([Board objects](Rewrite-1.1.1#the-board)), under `board`, with two things beside it that opening it needs: `format`, the version of the file format, which today's files lack, so that a file still to convert is told apart; and `packages`, the version of every package that the board's block classes, its front-end and its front-end's state come from, which R loads and migrations key on. A block of a class defined outside a package is there by its registry id alone, as any other, and nothing of its class is ([Board objects](Rewrite-1.1.1#block-classes-outside-a-package)). It names no R class or constructor, since the client holds none: when the client opens the file, it finds each block's class among the block registry's entries by registry id, and the board's front-end by its `front_end.id`. The client alone writes it, from its board and from the package versions R sends with the block registry, while R's `blockr_ser()`, for an app's opening board, writes each value as the client does wherever a schema gives the value's shape (below), but with the board's collections as arrays and without the ids the script left out, which the client mints ([Board objects](Rewrite-1.1.1#ids)), as fixtures that both test suites round-trip check ([Defining a board in R](Rewrite-1.1.3#writing-the-opening-board)). The client refuses a file whose `format` is higher than any it knows, with an error that names both versions, as it stops on a major protocol version it does not speak ([Wire protocol](Rewrite-1.1.9#handshake)), and so does R for the file `serve()` is given.

A board with two blocks, one of them of a class defined outside a package, a link and a board option:

```json
{
  "format": 1,
  "packages": { "blockr.core": "0.2.0" },
  "board": {
    "id": "curious_otter",
    "front_end": { "id": "blockr.core-basic", "state": {}, "attrs": {} },
    "name": "Sales review",
    "blocks": {
      "a": { "registry_id": "blockr.core-dataset_block", "state": { "dataset": "iris", "package": "datasets" }, "name": "Iris", "attrs": {} },
      "b": { "registry_id": "my_block", "state": { "n": 3 }, "name": "Mine", "attrs": {} }
    },
    "links": { "ab": { "from": "a", "to": "b", "input": "data" } },
    "stacks": {},
    "options": { "n_rows": 50 }
  }
}
```

A file from today's stack has another shape, in which every object, the board, its blocks, links, stacks and board options and the collections that hold them, is an `object`, its class vector, a `payload`, its constructor's args, and a `constructor`, the function with its package and that package's version at save time ([R/utils-serdes.R#L124-L142](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serdes.R#L124-L142)), and a dock board writes `extensions`, `views` and `grids` next to `blocks`, `links`, `stacks` and `options`, each extension with its class, its state and its constructor ([blockr.dock R/utils-serdes.R#L47-L95](https://github.com/BristolMyersSquibb/blockr.dock/blob/fd806ec45fd7158c32ae13b59cdca9386f34a985/R/utils-serdes.R#L47-L95)). A conversion outside core turns it into a saved file once: it maps its constructors to registry ids, picks a front-end by the class of the board it builds ([Board objects](Rewrite-1.1.1#the-board)), and maps what packages added onto the front-end's state by a convention that follows today's shape alone. A component the board adds next to core's `blocks`, `links`, `stacks` and `options` becomes a key of the same name in the front-end's state, so the dock's `views`, `grids` and `extensions` become the dock's `views`, `grids` and `extensions`, while within `extensions` each entry, which names a constructor of its own, goes under the id of the extension that constructor makes and keeps its constructor's args as its keys, so the `positions` of the DAG's entry become `positions` under the DAG's id. The converted file records in `packages` the version of each package that the nearest constructor records. A key of a block's payload that is neither a state arg nor `block_name`, such as the dock's `visible`, which core keeps now, becomes an attribute of the block ([Board objects](Rewrite-1.1.1#blocks)).

Writing one is `JSON.stringify()` in the browser, and opening one is the client's too, whether the user opens it with `store.open()`, a startup module names it, or `serve()` was given its path, which R passes on as it is, having read nothing of it but its format and the packages it names, which it loads ([Defining a board in R](Rewrite-1.1.3#the-opening-board), [Board updates](Rewrite-1.1.2#opening-a-board)). A file without a `format`, from today's stack, is converted first, outside core, by a conversion that reads it with typedjson, since only typedjson resolves the tags today's core writes, such as `"by": {"~t":"character","~v":[]}` for a merge block's empty `by`, and a file blockr.session wrote as `rack_load()` does (notes). It does so in a mode that refuses symbols, calls, closures and environments, `code = FALSE`, which typedjson added after 0.1.2 ([nbenn/typedjson#122](https://github.com/nbenn/typedjson/pull/122)), since 0.1.2 turns the tags a crafted file holds into code, which `bquote()` would then splice into a block's expression, against condition 5.

The client opens a file of the new stack by its ids: it has R load the packages that `packages` names, which registers their block classes, while a class from no package is one the app has registered already, runs the migrations below on what the file holds, block states included, drops and names what the app cannot rebuild ([Board objects](Rewrite-1.1.1#objects-that-cannot-be-rebuilt)), and gives each board option that the file lacks the `default` that its schema gives (below), while the store drops the keys and attributes of packages the app does not load ([Board updates](Rewrite-1.1.2#the-front-ends-state-and-attributes)). The conversion of a file from today's stack reads it with `blockr_deser()`, which dispatches on its class vectors and builds R objects to convert it, and leaves unread the closures today's files hold.

### State values between the client and R

The client's board holds state as its UI wrote it, plain JSON, in the shape of the JSON Schema that the class's UI module ships beside it ([UI modules in JS](Rewrite-1.1.7#packaging)). The UI owns that shape, since R takes an arg in several forms and could declare them only through unions of types (notes), and the class's author makes the values fit the expression its `expr` builds from them, since they enter through the UI.

R decodes what the client sends with yyjsonr, turning neither an array of objects into a data frame nor an array of arrays into a matrix, keeping a string in an array of numbers a string, and reading a 64-bit integer as a double: an array of one type becomes an atomic vector, an array of several types a list, an object a named list, and a string stays a string, so that nothing becomes code by being decoded ([Wire protocol](Rewrite-1.1.9#decoding)). A class's author writes `expr` against that decoding, as a Shiny author writes against an input's value. The jsonlite package decodes the same, except that it turns `[1, "a"]` into `c("1", "a")` (notes).

R writes state only where it makes it: for an app's opening board ([Defining a board in R](Rewrite-1.1.3)) and for a class's starting state in its block registry entry ([Block classes in R](Rewrite-1.1.5#registration)), while the conversion writes the state of every block of a file from today's stack, which it converts through R objects (above). R opens no board, so every other state stays in the client as the client wrote it. Where R writes state, it writes each value by the schema of its class's state, which R sends with the class's registry entry, since R's lack of scalars stays in R ([State in JS](Rewrite-1#principles)): a value of length one as an array where the schema has an array, and bare where the schema has a scalar or allows either, as the union `string | string[]` does, as condition 3 asks. A class whose UI ships no schema has such values written bare, so its UI takes either form. The arg specs keep describing args for models and tools ([Client-owned board state](Rewrite-1.1)), while the schema gives their shapes.

R writes the rest of a board it writes by schema too, so that no shape depends on R's JSON writer: core's objects by a JSON Schema of the board that core generates from the TypeScript types of [Board objects](Rewrite-1.1.1#the-board), so that a stack's `blocks` stays an array and an empty collection an object, and a key of the front-end's state or a board option's value by the schema its package ships beside its startup module ([UI modules in JS](Rewrite-1.1.7#packaging)), so that `show_conditions` set to `"error"` through a blockr option still reaches the client as the array its schema has. That needs no JSON writer of its own: R marks a value that the schema has as an array with `I()`, and an empty one that it has as an object as a named list, which yyjsonr, jsonlite and Shiny's encoder all keep (notes).

### Migrations

Everything a file holds migrates in JS, as the client opens it, through the one migration each package registers, which reads everything the file holds for every package, the front-end's state, the blocks' states and attributes and the board option values, and returns its own package's part in today's shape, the states of its block classes' blocks included, given the version of the package that saved it, from `packages` ([Board updates](Rewrite-1.1.2#the-front-ends-state-and-attributes)). A block class's UI owns the shape of its state and ships its schema (above), so the package that ships the UI migrates the state when that shape changes, and no migration runs in R. A package can thus rename, split and merge its keys, attributes, board options and state args between versions, and take over state that an earlier version of another package kept, and the store drops what no loaded package registered only once every migration has run. A file from today's stack migrates once, as its conversion outside core reads it, through the `blockr_deser()` methods its package has for each block's class, which read the version its `constructor` records or the shape of its payload, as blockr.dplyr's sixteen do ([R/legacy-deser.R#L30-L310](https://github.com/BristolMyersSquibb/blockr.dplyr/blob/bdac6b38f7097425bfe96883032531cc919f6ee7/R/legacy-deser.R#L30-L310)), and the client's migrations take over from the versions the converted file records, reading its front-end's state as the conversion writes it after typedjson read it, with a value of length one bare, so that they take either form there.

### Board options

A saved board holds each board option's value under its id and nothing else of it, so a board opened from one keeps the values it was saved with, while R computes initial values, from the board option constructors, only for the board an app script builds ([Defining a board in R](Rewrite-1.1.3#board-options)). When the client opens a board, it gives each board option that the board's parts require, its front-end, its block classes and the renderers R picked, and that the file lacks, the `default` that its schema gives, while the package that ships a board option defines it in the client ([Board objects](Rewrite-1.1.1#board-options)). A package's migration converts its board options' values with the rest of its state (above), and the store then drops and names a value that no board option claims, as it drops a key of the front-end's state that no loaded package registered, while a board option that a part requires but no installed package defines is an error naming both. The conversion of a file from today's stack drops a board option's category and label, since its definition supplies them.

Decoding the JSON a client writes, measured on the 4-core dev workspace with R 4.5.3, yyjsonr 0.1.22, jsonlite 2.0.0, typedjson 0.1.2 and shiny 1.14.0, each value inside an object as a block's state holds it, and yyjsonr with `obj_of_arrs_to_df`, `arr_of_objs_to_df` and `arr_of_arrs_to_matrix` off and `int64 = "double"`:

| JSON | yyjsonr | `jsonlite::fromJSON()`, no data frames or matrices | `typedjson::json_read_str()` | Shiny's input value |
|---|---|---|---|---|
| `["a"]` | `"a"` | `"a"` | `"a"` | `list("a")` |
| `[]` | `list()` | `list()` | `list()` | `list()` |
| `[1, "a"]` | `list(1L, "a")` | `c("1", "a")` | `list(1L, "a")` | `list(1L, "a")` |
| `[1, null]` | `c(1L, NA)` | `c(1L, NA)` | `list(1L, NULL)` | `list(1L, NULL)` |
| `[{"col": "a", "vals": ["x"]}]` | `list(list(col = "a", vals = "x"))` | the same | the same | `list(list(col = "a", vals = list("x")))` |
| `[[1, 2], [3, 4]]` | `list(1:2, 3:4)` | the same | the same | `list(list(1L, 2L), list(3L, 4L))` |
| `3`, `3.0` | `3L`, `3` | the same | the same | the same |
| `"~:x"`, `"~~a"` | `"~:x"`, `"~~a"` | the same | the symbol `x`, `"~a"` | `"~:x"`, `"~~a"` |

At its defaults `jsonlite::fromJSON()` turns the array of objects into a data frame and the array of arrays into a matrix. Shiny reads a message with `simplifyVector = FALSE` ([shiny R/server.R#L100-L109](https://github.com/rstudio/shiny/blob/dffc756a2867533fafc0858baf4c3fdbed165692/R/server.R#L100-L109)) and then unlists an input value that is an unnamed list ([R/server-input-handlers.R#L78-L98](https://github.com/rstudio/shiny/blob/dffc756a2867533fafc0858baf4c3fdbed165692/R/server-input-handlers.R#L78-L98)), so a message sent with `Shiny.setInputValue()` that is an array of requests reaches R as one flat named character vector. The other way, Shiny writes what `session$sendCustomMessage()` sends with `auto_unbox = TRUE`, which unboxes every length-one vector not wrapped in `I()`, and inserts a string of class `json` as it is ([R/shiny.R#L34-L52](https://github.com/rstudio/shiny/blob/dffc756a2867533fafc0858baf4c3fdbed165692/R/shiny.R#L34-L52)), so R marks each value that a schema has as an array with `I()`, and yyjsonr's and jsonlite's writers, with `auto_unbox = TRUE`, keep `I()` the same way. Marked as `list(stacks = setNames(list(), character()), s1 = list(blocks = I("a"), name = "Input"), cols = I(character()), na = NA_character_)`, a value comes out of all three as `{"stacks":{},"s1":{"blocks":["a"],"name":"Input"},"cols":[],"na":null}`, while unmarked, a one-block stack's `blocks` comes out bare and an empty `stacks` as `[]`. A schema is JSON Schema, so R reads where it has an array from its `type`, `items`, `properties` and `additionalProperties`, follows `$ref` into `$defs`, which Zod's `z.toJSONSchema()` writes for a type used twice, and takes `anyOf` and `oneOf` as allowing either form.

A file from today's core holds typedjson's tags wherever plain JSON cannot say a type, such as `"by": {"~t":"character","~v":[]}` for a merge block's empty `by`, which `JSON.parse()` reads as an object and only typedjson resolves to `character(0)`. Read with typedjson, a file blockr.session wrote comes back as `rack_load()` reads it. Version 0.1.2 also turns `{"~t":"language","~v":["~:Sys.getenv","HOME"]}` into the call `Sys.getenv("HOME")`, which `bquote()` splices into an expression, and the string `"~:x"` into the symbol `x`, so the conversion reads today's files in the mode that refuses those tags, `code = FALSE`, which typedjson added after 0.1.2 ([nbenn/typedjson#122](https://github.com/nbenn/typedjson/pull/122)). A file of today's stack is told by its missing `format`.

Of the 177 state args of the 46 classes that blockr.core 0.1.4, blockr.dplyr 0.2.0.9035, blockr.dm 0.0.92, blockr.ggplot 0.1.1.9010 and blockr.io 0.1.0.9015 register, 29 declare no type in R today: seven args of blockr.dm's crossfilter block, the `state` of its two filter blocks and the `args` of its read block, the `args` of blockr.io's read, write and download blocks and the write block's `mode`, nine labels and settings of blockr.ggplot's plot block, five args of blockr.dplyr's pivot, rename, separate and slice blocks, and the `volumes` of core's file browser, a named character vector, which plain JSON brings back as a named list. No `arg_object()` describes a free-form `args` list, since it describes a closed record, while the read block's UI knows which of its settings are arrays.
