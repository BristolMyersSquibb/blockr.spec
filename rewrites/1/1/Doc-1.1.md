# Client-owned board state
Status: settled on 2026-10-23. Part of [State in JS](Doc-1).

This part covers blockr.core: the client's document store, command registry and scheduler, the registry export, block types and their UIs, and R's per-session evaluator. Every other part builds on it, and its design pages set out each API.

## Problem

Board state lives in R. The `board_server()` function holds the blocks and their args, links, stacks and options, and runs board management, block construction, demand and visibility gating and every block's UI logic as Shiny reactives in the session's R process, on its one thread. Evaluation, the only part that needs R, waits behind all of it. [State in JS](Doc-1#problem) sets out what this costs and what it has led to.

## What must hold

Conditions 1 to 5 of [State in JS](Doc-1#what-must-hold) rest on this part, and so does this one:

1. A block's R side is plain functions: its expression from its state and data inputs, and what its UI needs from the same.

## Proposal

- The board is a document held by a TypeScript store in core's JS API: blocks as registry id plus args, links, stacks and options, plus the fields a board subclass adds, such as the dock's views and layouts ([Client-drawn dock and extensions](Doc-1.2)), in the [document model](Doc-1.1.1), while a saved board keeps the shape `blockr_ser()` writes today, naming each object's constructor ([Serialization](Doc-1.1.4)). Every edit, by the user or the assistant, is a versioned delta in the `add`, `mod` and `rm` shape of core's board updates, since that shape exists already in `update()` and in the assistant's staged edits, and the same deltas give undo. Opening a board, at startup or later, is no delta: it goes through R and replaces the document ([Board updates](Doc-1.1.2)). Session management is out of scope: packages build it on the store and on requests they add, and a plain download and upload, if core ships one, only exercises the store's API.
- All edits run through one command registry in core, which menus, shortcuts, extensions and the assistant's tools call alike. It replaces dock's action registry and core's plugins, and core keeps no plugin or extension type of its own: a plugin's logic becomes commands and its UI a dock extension ([Client-drawn dock and extensions](Doc-1.2)), as [blockr.code#8](https://github.com/BristolMyersSquibb/blockr.code/issues/8) does for code export. Saving and restoring needed core today, since a restore is a `session$reload()` that the app's `board_loader()` handles; here the store opens a board in place of the whole document ([Board updates](Doc-1.1.2)), which is all session management needs.
- Whatever does not need R moves to the browser. R is an evaluator, one process per session. A result is named by its block id and a version, which the client bumps on every change to the block or to anything upstream of it, the way spreadsheets and notebooks track their cells, and never by process, so putting several sessions on one process, or one session on several, stays a server-side change. A request carries the recipe, the block's registry id and args with its inputs as block ids and versions, so a lost process costs only recomputation. A result is any R object, shown through its block type's `output`, which can dispatch on the result's class, so nothing in the protocol assumes a table. Board options never reach a type's `interpolate`: one that shapes outputs redraws them without re-evaluating, the `evaluation` option decides what the client demands, and a block that reads relative to a directory takes the directory as an input.
- The client schedules. On an edit it marks the block and everything downstream stale, keeps the last results on screen, and requests what is demanded, and everything upstream of it, in topological order, which replaces construction ordering, the render gate and the visibility channels in R. A board demands every block, as today, unless its `evaluation` option is lazy: then a block of a type declared eager, such as one that writes a file, is still demanded, the dock demands what it shows, in one owner-keyed set that every owner writes the same way, as [blockr#489](https://github.com/orgs/BristolMyersSquibb/discussions/489) has it for the R board, and a code export or the assistant evaluates what it reads once ([Evaluation in the client](Doc-1.1.10)). Any component may invalidate a block, such as a read block's reload, which bumps its version and everything downstream.
- There is no early cutoff and no hashing of results in the foundation: a recomputed R result is always a new object, so an identity check would never fire, and a hash costs time in proportion to a result's size and means nothing for environments, external pointers or lazy tables. Cutoff can come later, opt-in per block type.
- A block stays an S3 object made by its constructor, and the board a startup script builds from such objects becomes the client's opening document. A block type is a value defined once, holding its UI, inputs, requests and the functions R evaluates a block with, and its constructor is made from it ([Block types in R](Doc-1.1.5)). R calls a block's constructor only where a board is built, in an app script and when a board is opened, and evaluates a block by calling its type's functions: `validate` checks the recipe's state, `interpolate(x, state, inputs)` builds the expression from the state and the data inputs, which R holds when it evaluates, so data-dependent logic can keep writing clean interpolated code, and `evaluate` runs it, while R keeps results by block id and no state ([blockr.core#400](https://github.com/BristolMyersSquibb/blockr.core/issues/400)). The arg specs describe args for LLMs and tools and are not checked at run time, since a block's UI decides their shapes.
- A block's UI is composed in R from a set of input elements core ships, much like a Shiny UI. An attribute that depends on the data is an R function whose arguments name the inputs and state args it reads, such as `max = \(data) nrow(data)`, and the client asks R for it again when one of those changes, so R holds no reactive graph. A block that needs a richer UI ships its own ES module, which receives an injected host holding its state, `submit()`, `request()` and core's elements, and gets other packages' modules through the host too. React reaches it through its build instead, since React libraries import `react` themselves as they load: a preset maps `react` to the copy the dock puts on a global core names ([blockr.core#399](https://github.com/BristolMyersSquibb/blockr.core/issues/399)). The JSON such a module exchanges with R is private to its block type, and a React SDK on top is the usual way to write one ([Client-drawn dock and extensions](Doc-1.2)). A board option keeps its R constructor and gets its UI the same way, from the elements or a module of its own, so R only ever sees option values.
- Core has a JS API and an R API, with a versioned wire protocol between them that both sides test against shared fixtures, as shinyreact does.
- R builds every expression with the block type's `interpolate`, so the code a block shows and exports is the code that ran. The only safety is in how R decodes what the client sends: into plain values, never closures, calls, symbols or environments, so nothing becomes code by being decoded, and `bquote()` keeps a value a value. A string still becomes code wherever a block parses one, as most of blockr.dplyr's builders do, so a board can run any R code, and limiting what the R process may do is the deployment's job, such as a sandbox around it. So is access: core knows nothing about users, since access is the data source's, through the process's file permissions or an API client's own token, and results are never shared between sessions, since what a read returns can depend on who runs it. A reply carries its status, conditions and output, and the client decides what to show, so `show_conditions` becomes a display setting.
- Other requests are registered per block type, or per package for work that belongs to no single block and needs R or the server, such as code generation in blockr.code, or exchanging a visitor's Connect session token, which only the content's process receives, for the key that session management's storage calls then use from the browser ([Session management extension](Doc-1.6)). A block type's request reads the block's inputs or its result at given versions and never reads block state implicitly, so the client can cache its answers by version and arguments, while a package's request is not cached, since it may write, and may name blocks and versions whose results it reads, which are evaluated first. There is no generic request for a column's values: a value list is a block type's own request, bounded by its author. Effects need no mechanism of their own: a write is a block's expression, a manual save a click that bumps its state, a download a result whose output hands the file over, and an upload a request carrying the file.
- Shiny stays as host and transport for now, since on Connect a Shiny app with *Max connections per process* at 1 gives each session its own process. A small bridge module over `Shiny.setInputValue()` and `Shiny.addCustomMessageHandler()` carries the protocol, rather than shinyreact, whose API is React hooks and components and has no request and response. Leaving Shiny later replaces that module.

## Work

- Write the wire protocol, with the recipe and version formats, requests that packages add, status, conditions and errors, the handshake with capabilities, and binary bodies, as a versioned document with shared fixtures, in blockr.core ([blockr.core#393](https://github.com/BristolMyersSquibb/blockr.core/issues/393))
- Build the client document store, with versioned deltas and undo, and the command registry, in blockr.core ([blockr.core#394](https://github.com/BristolMyersSquibb/blockr.core/issues/394))
- Build the client scheduler, which bumps versions downstream of an edit and requests the necessary set in topological order, in blockr.core ([blockr.core#395](https://github.com/BristolMyersSquibb/blockr.core/issues/395))
- Export the block registry for the client, with registry ids, default args, input slots, arg specs and UIs, in blockr.core ([blockr.core#396](https://github.com/BristolMyersSquibb/blockr.core/issues/396))
- Define block types as values with `block_type()`, holding their evaluation functions and requests, and port the built-in blocks, in blockr.core ([blockr.core#397](https://github.com/BristolMyersSquibb/blockr.core/issues/397))
- Ship the input elements block UIs are composed of in R, with data-dependent attributes as functions of the block's inputs and state, in blockr.core ([blockr.core#404](https://github.com/BristolMyersSquibb/blockr.core/issues/404))
- Load a block type's UI module on first use and mount it with an injected host, in blockr.core ([blockr.core#398](https://github.com/BristolMyersSquibb/blockr.core/issues/398))
- Build the React SDK for block UIs, with `useBlockState()` and `useBlockData()` over the injected host, in blockr.core ([blockr.core#399](https://github.com/BristolMyersSquibb/blockr.core/issues/399))
- Build the per-session evaluator, holding the latest result of each block, and the Shiny bridge, in blockr.core ([blockr.core#400](https://github.com/BristolMyersSquibb/blockr.core/issues/400))
- Add the block type's output, which describes a result for the client, with a `tabular_output()` hook for tables, a method for data frames and a default that prints, in blockr.core ([blockr.core#401](https://github.com/BristolMyersSquibb/blockr.core/issues/401))
- Load documents written by today's `blockr_ser()` into the client store, in blockr.core ([blockr.core#402](https://github.com/BristolMyersSquibb/blockr.core/issues/402))
- Write the guide for block type authors, covering state shapes, building expressions from values, bounded requests and outputs, in blockr.core ([blockr.core#403](https://github.com/BristolMyersSquibb/blockr.core/issues/403))
