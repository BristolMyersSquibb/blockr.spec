# Defining a board in R for the client-owned board
Status: settled on 2026-10-28. Design for [Client-owned board state](Rewrite-1.1).

One of the API proposals for the client-owned board ([Client-owned board state](Rewrite-1.1)): the R code that defines and launches an app, and how the board it builds becomes the client's opening board. It builds on the [board objects proposal](Rewrite-1.1.1) and the [serialization proposal](Rewrite-1.1.4), and shapes serving a board with `serve()`, opening boards in R, writing saved boards in the client and porting core's built-in blocks, each an item in the Work list of [Client-owned board state](Rewrite-1.1#work). How a block class is written is the block classes proposal ([Block classes in R](Rewrite-1.1.5)), and how a front-end draws the board is [Front-ends and extension points](Rewrite-1.1.8)'s.

## What must hold

1. An app script keeps the shape it has today: `serve()` around a board constructor that takes blocks, links, stacks, options and, for the dock, extensions.
2. The board the script builds reaches the client as the same JSON a saved board is, and R keeps nothing of it that an edit changes.
3. A block class defined in the app script works where R evaluates no definition from a file, as in a deployment.
4. R's `blockr_ser()` and the client write the same file for the same board, wherever a schema gives each value's shape.
5. Serving a single block while developing it, and serving a saved file, work as today.
6. Data that a script hands to `serve()` stays in R, so no board, file or request carries it.
7. An app sets its blockr options as today, through `blockr_option()`, and the board holds none of them, so its JSON describes the board in full.
8. An object an app script builds holds its class and what its counterpart in the client's board holds, its id, name and state, and nothing else.

## Proposal

### The script

That script stays as it is, while the objects its constructors return hold only what their counterparts in the client's board hold: each its class, its id, name and state, and a block its attributes too ([Board objects](Rewrite-1.1.1#the-board)). A block holds its state, name and attributes and refers to its block class ([Block classes in R](Rewrite-1.1.5)), a link its ends, input and name, a stack its blocks and name, and the board its front-end, blocks, links, stacks, option values, name and the fields packages add to it ([Board objects](Rewrite-1.1.1#extending-cores-objects)). The Shiny servers and UI functions they hold today go, and a board's plugins become commands and extensions.

The constructors keep the arguments that carry such state, and `class`, through which a constructor that extends a board, a link or a stack, such as `new_dock_board()` or `new_dock_stack()`, names its class in R ([R/board-class.R#L38-L62](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/board-class.R#L38-L62), [R/stack-class.R#L47-L78](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/stack-class.R#L47-L78)). Their `ctor` and `pkg` arguments go, since a saved file names no R constructor ([Serialization](Rewrite-1.1.4#files)) and R needs none to open one: it opens the file on its JSON (below), where it finds each block's class in the block registry by its registry id ([Block classes in R](Rewrite-1.1.5)), and leaves a board made for another front-end as it is, for the app's front-end to draw ([Front-ends and extension points](Rewrite-1.1.8#registering-a-front-end)). A board names its front-end instead, which its constructor sets, `blockr.core-basic` for `new_board()` and `blockr.dock-dock` for `new_dock_board()`. A script passes neither argument, and what a package adds to a link or a stack lives in a field of its own in the client's board, which carries no class ([Board objects](Rewrite-1.1.1#extending-cores-objects)). The dock's `new_dock_board()` keeps its extensions, views, grids and active view ([R/dock-board.R#L55](https://github.com/BristolMyersSquibb/blockr.dock/blob/fd806ec45fd7158c32ae13b59cdca9386f34a985/R/dock-board.R#L55)), all of which a board needs to open, save and restore ([Client-drawn dock and extensions](Rewrite-1.2)), while an option's constructor takes its value alone, since the package that ships the option defines the rest in the client, its label, category, schema, UI and what a new value does ([Board objects](Rewrite-1.1.1#options)), and only two tests set a label or a category today. Of these, `new_board()` and `new_link()` gain a `name`, since every object has one, and the board's name replaces core's `board_name` option, while `new_board()` also takes the board's `id`, which `serve()` takes today (below). No block holds data in its state (below).

In R, these objects become a definition language that R translates to JSON: constructors that build and check them, `blockr_ser()` that writes them and the accessors it uses. R opens a board given as JSON without building them, except a file from today's stack, which `blockr_deser()` reads into them to convert it ([Board objects](Rewrite-1.1.1#the-board)). Nothing changes a board in R, since every change is a delta in the client ([Board updates](Rewrite-1.1.2)), so core's setters and modifiers go (notes). Every caller of them in the workspace is server code that moves to the client, except one script: CEDX derives its board from another with `rm_blocks()` and `board_links<-` ([R/cedx_board.R#L1072-L1092](https://github.com/BristolMyersSquibb/blockr.cdex/blob/7792b7e0fd9eda417995dd7e460f086f671df73c/R/cedx_board.R#L1072-L1092)), and builds it from that board's parts instead. The containers that hold blocks, links and stacks need only be built and checked once, by the board's constructor, so of today's vctrs vectors and records they keep what a script builds with, such as `c()` on blocks, and lose the methods that keep them valid under modification, such as `names<-` ([R/blocks-class.R#L80-L94](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/blocks-class.R#L80-L94)), `[<-` and `[[<-` ([#L156-L202](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/blocks-class.R#L156-L202)).

### The opening board

An app gives its board in one of two ways, and both end in the same JSON, the schema the client saves a board in ([Serialization](Rewrite-1.1.4#files)). Built with constructors, as the script above builds it, the board is converted to that JSON once, when `serve()` is called as the script's top level runs: R collects its options, registers the block classes its blocks refer to, from the blocks themselves, and writes it with `blockr_ser()`. Given as JSON, as a path given to `serve()` is, it is that JSON already, and R opens it as it opens every board it did not build itself, the board a client sends with its `hello` after R restarts and the one `store.open()` sends ([Board updates](Rewrite-1.1.2#opening-a-board)): it loads the packages the board names and registers their block classes, migrates blocks saved by older versions of them, gives each option the file lacks the app's initial value and drops what it cannot rebuild, all on the JSON, building no R board ([Board objects](Rewrite-1.1.1#the-board)). R sends that JSON with every reply to a session's `hello`, beside the block registry's entries ([Wire protocol](Rewrite-1.1.9#handshake)). So the opening board holds nothing a saved file cannot, such as a closure in a block's state, and a board the format cannot hold fails when the script runs, not when a session starts. From then on the client owns the board, and R holds the session's results and, for the process, the opening board's JSON, which no edit changes.

Registering the classes first keeps an app's own block classes working. A class defined in the app script reaches the JSON only as a definition, its source ([Board objects](Rewrite-1.1.1#block-classes-outside-a-package)), and R evaluates a definition only where the `load_definitions` option allows it, which a deployment does not by default, so if the script's board were only JSON, a deployed app would drop its own blocks. Registered from the blocks, as [Board objects](Rewrite-1.1.1#the-board) has it for a board from a constructor call, each class is in the block registry before any session evaluates a block of it, and no definition is evaluated. These registrations are the app script's own, so they stay when another board is opened, as a fresh app would have them, while a class a file registers goes with that file's board, since opening a board leaves the app exactly as opening it in a fresh app would ([Board updates](Rewrite-1.1.2#what-must-hold)). A board saved from the app holds the script's classes only as definitions, and a deployment reopens it only while those classes stay registered.

The `loader` argument goes, since neither of today's loaders keeps its job: `store.open()` replaces the board in place, so no reload needs `local_loader()` to carry a board across it ([Board updates](Rewrite-1.1.2#opening-a-board)), and session management opens the board a URL names from the browser, which makes every storage call ([Session management extension](Rewrite-1.6)). So R writes the opening board once per process and sends it to every session. A locked session shows its script's board, since it opens no board a client sends ([Wire protocol](Rewrite-1.1.9#locked-boards)), and no app today picks a locked session's board in R. What remains of the loader is an ordering on the client: where `rack_loader()` resolves the board a URL names before the page is drawn, session management fetches it from its package's startup module a few round trips after the `hello`, and core opens it in place of the script's board, before anything is drawn or evaluated ([Front-ends and extension points](Rewrite-1.1.8#starting-the-page)).

### Writing the opening board

R's `blockr_ser()` writes the opening board and the client writes every board that is saved, so both write the format of [Serialization](Rewrite-1.1.4#files), the board with its `format`, the versions of its packages and the definitions of block classes defined outside a package, and both must write the same file for the same board, which they do by the same schemas, those of the board, of each block class's state and of each field ([Serialization](Rewrite-1.1.4#state-values-between-the-client-and-r)). Fixtures that both test suites round-trip hold the two together, as they do the messages of [Wire protocol](Rewrite-1.1.9): each is a board as constructor calls, the file R writes for it, and the board and block registry entries R opens that file to, from which the client must write the same file again.

The opening board is where every app meets R's lack of scalars, since R writes the state of the script's blocks: `new_merge_block(by = "Time")` holds `by` and `all_x` as vectors of length one, and the client needs the first as `["Time"]` and the second as `false`, which R writes by the schema that the merge block's UI ships for its state ([Serialization](Rewrite-1.1.4#state-values-between-the-client-and-r)).

### The `serve()` generic

The `serve()` generic and its three methods stay. For a board, `serve.board()` starts a Shiny app whose page loads core's client and the front-end the board is made for, such as the dock for a board whose `front_end` is `blockr.dock-dock`, and whose server carries the protocol and evaluates. R reads the front-end off the board the script builds, or off the file `serve()` is given ([Board objects](Rewrite-1.1.1#the-board)), and the `blockr_app_ui()` and `blockr_app_server()` methods go, since a package now declares a front-end in R by its name and module, which the page loads ([Front-ends and extension points](Rewrite-1.1.8#registering-a-front-end)). The board's id moves from `serve()`, where it is the board's namespace today, to the board: `new_board()` takes an `id`, which it draws at random when the script runs unless the script fixes one, as `serve()` draws its `id` today ([R/utils-serve.R#L120-L132](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L120-L132)), so a script that passes an id to `serve()`, as the dock app above passes `"my_board"`, passes it to the board's constructor instead. A board given as JSON keeps the id it holds, whether `serve()` is given its path, the client opens it with `store.open()` or sends it with its `hello` after R restarts ([Board objects](Rewrite-1.1.1#the-board)). For a block, `serve.block(x, data = list(...))` serves the block and its data with no board around them, as today (below). For a path, `serve()` keeps the file in place of the JSON it would write, and opens it with the migrations of [Serialization](Rewrite-1.1.4#migrations). The new stack's `serve()` has no `plugins` argument, since core keeps no plugin or extension type of its own: a plugin's logic becomes commands and its UI a dock extension, and the notes of [Client-drawn dock and extensions](Rewrite-1.2) map each of today's nine plugins to its new home. Nothing else of today's `serve()` carries over, since each piece serves the R board or its UI, and what the new stack still needs of them it builds anew: the `options` argument that `custom_options()` fills, since a board's options are those its parts require (below); `blockr_test_exports()`, through which shinytest2 reads the block servers' results and the dock's sync counters; what `serve()` passes through `...` to a front-end's UI, such as the dock's `navbar`, whose items become extensions' contributions on the client ([Client-drawn dock and extensions](Rewrite-1.2)); and the URL's query, which the client reads itself.

### Data passed to `serve()`

A single-block app is for a block's developer, who serves the block with fixed data, as `serve(new_head_block(), data = list(data = iris))` does, and it has no board, as today: the page shows the block's UI and its output and nothing around them, and nothing in the app can change the data ([R/utils-serve.R#L36-L91](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L36-L91)). Core's client mounts both through the same `mountBlock()` and `mountOutput()` a front-end uses ([Front-ends and extension points](Rewrite-1.1.8#what-core-gives-a-front-end)), and keeps the block's state in its store and evaluates it with its scheduler, as it does a block on a board, so the page needs no runtime of its own, while nothing draws, saves or opens the block as a board, and the `hello` reply carries it as a board of one block, which only the store sees. R keeps the data for the process and binds each entry to the block's input of that name whenever it evaluates the block, as today's `serve.block()` hands the data to the block's server, so the evaluation requests name no input for a slot R binds, and the data reaches neither a file nor the client, except as the block's output.

A board takes no data from `serve()`, since its data comes from its data blocks, and core's static block is the plainest of them: a block whose state is one expression without parameters, given as a string, which R evaluates for the block's result and shows as its code, such as `new_static_block("iris")`, `new_static_block("head(iris)")` or `new_static_block("safetyData::adam_adsl")`. Its state holds code and never data, so the board, its files and its requests carry the expression while the data stays in R, and the code exported for the board reproduces the data. Today's `new_static_block()` holds a data frame in its state and reads it back from its constructor's environment ([R/data-static.R#L12-L36](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/data-static.R#L12-L36)), and the tests and examples that call it with a data frame, such as blockr.ui's and blockr.dm's example apps ([inst/examples/table-preview/app.R#L29](https://github.com/BristolMyersSquibb/blockr.ui/blob/9bd8312a3408bbcbabff2b57d1d3fd5681843c94/inst/examples/table-preview/app.R#L29), [blockr.dm inst/examples/filter-demo/app.R#L38](https://github.com/BristolMyersSquibb/blockr.dm/blob/938428bce5a488f2479034eef088f86a5053e09d/inst/examples/filter-demo/app.R#L38)), give it an expression instead, as blockr.ui's can with `"safetyData::adam_adsl"`.

### Options

A board's options are those its parts require, declared as today through `options = default_board_options()`, the board options the app's front-end declares ([Front-ends and extension points](Rewrite-1.1.8#registering-a-front-end)), and the `options` field of block classes ([Block classes in R](Rewrite-1.1.5#generics)). R collects them, with those of every class the block registry holds, keeping one per id, as `blockr_app_options()` collects them ([R/utils-serve.R#L172](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L172)), each time it opens a board, as for a file, and an option that a part requires but no installed package defines is an error naming both. What the board holds is their values: R names each option by its id, with the initial value its constructor computes, such as `blockr_option("n_rows", 50L)` for `n_rows`, and the package that ships the option defines the rest in the client, its label, category, schema, UI and what a new value does ([Board objects](Rewrite-1.1.1#options)).

### Blockr options

An app fixes its blockr options when it starts or is deployed, as today: `blockr_option()` reads each from an R option `blockr.<name>` or an environment variable `BLOCKR_<NAME>`, which a deployment such as Connect sets without touching the script ([R/utils-misc.R#L247-L276](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-misc.R#L247-L276)). The mechanism carries over, while the blockr options follow the code that reads them: today's packages read 56, such as core's `show_conditions` and the dock's `view_tabs`, and each part keeps, drops or adds blockr options as it translates its code rather than copying it ([State in JS](Rewrite-1#principles)). A blockr option is fixed for the app, where a board option surfaces to the user, with its UI and logic, what changes while the app runs, so the board holds no blockr option, and its JSON describes the board in full. R reads the blockr options its own code needs where it needs them, as today, and sends the values of those the client reads with its reply to `hello` ([Wire protocol](Rewrite-1.1.9#handshake)), each package declaring which of its blockr options its client code reads. Core hands them to front-ends and extensions through `CoreApi` ([Front-ends and extension points](Rewrite-1.1.8#what-core-gives-a-front-end)), so client code has them passed in rather than reading a global ([State in JS](Rewrite-1#principles)).

A constructor argument that configures rather than holds state is lost to the JSON, which keeps what the board holds and nothing else. Such an argument becomes a blockr option where it is a value, and moves to the code that calls it where it is a function. The function `new_assistant_extension()` takes as its `system_prompt` ([vignettes/intro.Rmd#L124-L153](https://github.com/BristolMyersSquibb/blockr.assistant/blob/fd5865593fd8b015d00df9238e2e622475c2a9df/vignettes/intro.Rmd#L124-L153)), which a board restored from a file loses already ([R/ext-server.R#L1229-L1231](https://github.com/BristolMyersSquibb/blockr.assistant/blob/fd5865593fd8b015d00df9238e2e622475c2a9df/R/ext-server.R#L1229-L1231)), is R because ellmer runs the agent loop in R, and becomes JS logic of the assistant extension once that loop runs in the browser ([Assistant as a client extension](Rewrite-1.4)).
