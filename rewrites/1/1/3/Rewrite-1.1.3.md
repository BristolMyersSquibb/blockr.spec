# Defining a board in R for the client-owned board
Status: review. Design for [Client-owned board state](Rewrite-1.1).

One of the API proposals for the client-owned board ([Client-owned board state](Rewrite-1.1)): the R code that defines and launches an app, and how the board it builds becomes the client's opening board. It builds on the [board objects proposal](Rewrite-1.1.1) and the [serialization proposal](Rewrite-1.1.4), and shapes serving a board with `serve()`, opening boards in R, writing saved boards in the client and porting core's built-in blocks, each an item in the Work list of [Client-owned board state](Rewrite-1.1#work). How a block type is written is the block types proposal ([Block types in R](Rewrite-1.1.5)), and how a front-end draws the board is [Front-ends and extension points](Rewrite-1.1.8)'s.

## What must hold

1. An app script keeps the shape it has today: `serve()` around a board constructor that takes blocks, links, stacks, options and, for the dock, extensions.
2. The board the script builds reaches the client through the code that opens a saved file, and R keeps nothing of it that an edit changes.
3. A block type defined in the app script works where R evaluates no definition from a file, as in a deployment.
4. R's `blockr_ser()` and the client write the same file for the same board.
5. Serving a single block while developing it, and serving a saved file, work as today.
6. Data that a script hands to a board stays in R, so no board, file or request carries it.
7. An app sets what it configures as today, through `blockr_option()`, and the board holds none of those settings, so its JSON describes the board in full.
8. An object an app script builds holds its type and what its counterpart in the client's board holds, its id, name and state, and nothing else.

For a board, `serve.board(x, id, plugins, options, loader, ...)` combines `blockr_app_ui()` and `blockr_app_server()` ([#L204-L218](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L204-L218)), and blockr.dock implements those for `dock_board`, adding its navbar ([blockr.dock R/utils-serve.R#L2-L86](https://github.com/BristolMyersSquibb/blockr.dock/blob/fd806ec45fd7158c32ae13b59cdca9386f34a985/R/utils-serve.R#L2-L86)). ## Proposal

### The script

That script stays as it is, while the objects its constructors return become proxies for the client's: each holds its type and what the client's board holds for it, its id, name and state, and for a block its attributes, and nothing else ([Board objects](Rewrite-1.1.1#the-board)). A block holds its state, name and attributes and refers to its block type ([Block types in R](Rewrite-1.1.5)), a link its ends, input and name, a stack its blocks and name, and the board its front-end, blocks, links, stacks, option values, name and the fields packages add to it ([Board objects](Rewrite-1.1.1#extending-cores-objects)). The Shiny servers and UI functions they hold today go, and a board's plugins become commands and extensions.

The constructors keep the arguments that carry such state, and `class`, through which a constructor that extends a board, a link or a stack, such as `new_dock_board()` or `new_dock_stack()`, names its class in R ([R/board-class.R#L38-L62](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/board-class.R#L38-L62), [R/stack-class.R#L47-L78](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/stack-class.R#L47-L78)). Their `ctor` and `pkg` arguments go, since a saved file names no R constructor ([Serialization](Rewrite-1.1.4#files)): R finds a block's constructor through the block registry, by its type's registry id ([Block types in R](Rewrite-1.1.5)), a link's and a stack's in core, and a board's through the front-end the board names, which its constructor sets, `blockr.core` for `new_board()` and `blockr.dock` for `new_dock_board()`, and whose package declares that constructor ([Front-ends and extension points](Rewrite-1.1.8#what-goes-from-r)). A script passes none of these, and what a package adds to a link or a stack lives in a field of its own in the client's board, which carries no class ([Board objects](Rewrite-1.1.1#extending-cores-objects)). The dock's `new_dock_board()` keeps its extensions, views, grids and active view ([R/dock-board.R#L55](https://github.com/BristolMyersSquibb/blockr.dock/blob/fd806ec45fd7158c32ae13b59cdca9386f34a985/R/dock-board.R#L55)), all of which a board needs to open, save and restore ([Client-drawn dock and extensions](Rewrite-1.2)), while an option's constructor takes its value alone, since the package that ships the option defines the rest in the client, its label, category, schema, UI and what a new value does ([Board objects](Rewrite-1.1.1#options)), and only two tests set a label or a category today. Of these, `new_board()` and `new_link()` gain a `name`, since every object has one, and the board's name replaces core's `board_name` option. Data that the script holds in memory goes to `serve()` rather than into a block (below).

In R, these objects become a definition language that R translates to JSON and back: constructors that build and check them, `blockr_ser()` that writes them, a reader that builds them again when a board is opened, by registry id for a file of the new stack and with `blockr_deser()` for one from today's stack ([Board objects](Rewrite-1.1.1#the-board)), and the accessors these use. Nothing changes a board in R, since every change is a delta in the client ([Board updates](Rewrite-1.1.2)), so core's setters and modifiers go (notes). Every caller of them in the workspace is server code that moves to the client, except one script: CEDX derives its board from another with `rm_blocks()` and `board_links<-` ([R/cedx_board.R#L1072-L1092](https://github.com/BristolMyersSquibb/blockr.cdex/blob/7792b7e0fd9eda417995dd7e460f086f671df73c/R/cedx_board.R#L1072-L1092)), and builds it from that board's parts instead. The containers that hold blocks, links and stacks need only be built and checked once, by the board's constructor, so of today's vctrs vectors and records they keep what a script builds with, such as `c()` on blocks, and lose the methods that keep them valid under modification, such as `names<-` ([R/blocks-class.R#L80-L94](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/blocks-class.R#L80-L94)), `[<-` and `[[<-` ([#L156-L202](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/blocks-class.R#L156-L202)).

### The opening board

The script's board reaches the client the way a saved file does. When `serve()` is called, once per process as the script's top level runs, R registers the types the board's blocks refer to, from the blocks themselves, and writes the board with `blockr_ser()` as JSON in the format of [Serialization](Rewrite-1.1.4#files), which it keeps for the process. When a session's `hello` arrives, R opens that JSON as it opens a file: it reads it by its registry ids, as it reads any file of the new stack, registers its types, collects its options and turns it into the client's board, which it sends with the block registry's entries in its reply ([Wire protocol](Rewrite-1.1.9#handshake)). Every opening board thus comes from the same kind of JSON through the same code, whether it starts as a script, a path given to `serve()`, the board a client sends with its `hello` after R restarts, or `store.open()` ([Board updates](Rewrite-1.1.2#opening-a-board)). So the opening board holds nothing a file cannot, such as a closure in a block's state, and a board the format cannot hold fails when the script runs, not when a session opens it. From then on the client owns the board, and R holds the session's results and, for the process, the JSON it opens sessions from, which no edit changes.

Registering the types first keeps an app's own block types working. A type defined in the app script reaches the JSON only as a definition, its source ([Board objects](Rewrite-1.1.1#block-types-outside-a-package)), and R evaluates a definition only where the `load_definitions` option allows it, which a deployment does not by default, so if the script's board were only JSON, a deployed app would drop its own blocks. Registered from the blocks, as [Board objects](Rewrite-1.1.1#the-board) has it for a board from a constructor call, each type is found when the JSON opens, and no definition is evaluated. These registrations are the app script's own, so they stay when another board is opened, unlike a type a file registers: a board saved from the app holds such a type only as a definition, and a deployment reopens it only while the type stays registered.

The `loader` argument goes, since neither of today's loaders keeps its job: `store.open()` replaces the board in place, so no reload needs `local_loader()` to carry a board across it ([Board updates](Rewrite-1.1.2#opening-a-board)), and session management opens the board a URL names from the browser, which makes every storage call ([Session management extension](Rewrite-1.6)). So R writes the opening board once per process and opens it for every session. A locked session shows its script's board, since it opens no board a client sends ([Wire protocol](Rewrite-1.1.9#locked-boards)), and no app today picks a locked session's board in R. What remains of the loader is an ordering on the client: a board the URL names replaces the script's board a few round trips after the `hello`, where `rack_loader()` resolves it before the page is drawn, so an extension has to be able to replace the opening board before anything is drawn or evaluated ([Front-ends and extension points](Rewrite-1.1.8#open-questions)).

### Writing the opening board

R's `blockr_ser()` writes the opening board and the client writes every board that is saved, so both write the format of [Serialization](Rewrite-1.1.4#files), the board with its `format`, the versions of its packages and the definitions of block types defined outside a package, and both must write the same file for the same board. Fixtures that both test suites round-trip hold the two together, as they do the messages of [Wire protocol](Rewrite-1.1.9): each is a board as constructor calls, the file R writes for it, and the board and block registry entries R opens that file to, from which the client must write the same file again.

The opening board is where every app meets R's lack of scalars, since R writes the state of the script's blocks: `new_merge_block(by = "Time")` holds `by` and `all_x` as vectors of length one, and the client needs the first as `["Time"]` and the second as `false`, which R writes by the schema that the merge block's UI ships for its state ([Serialization](Rewrite-1.1.4#state-values-between-the-client-and-r)).

### The `serve()` generic

The `serve()` generic and its three methods stay. For a board, `serve.board()` starts a Shiny app whose page loads core's client and the front-end the board is made for, such as the dock for a board whose `front_end` is `blockr.dock`, and whose server carries the protocol and evaluates. R reads the front-end off the board the script builds, or off the file `serve()` is given ([Board objects](Rewrite-1.1.1#the-board)), and the `blockr_app_ui()` and `blockr_app_server()` methods go, since a front-end now registers on the client, under its package's name ([Front-ends and extension points](Rewrite-1.1.8)). Its `id`, the board's namespace today, becomes the id the JSON records for the board ([Board objects](Rewrite-1.1.1#the-board)), drawn at random once per process where the script gives none, as today. For a block, `serve.block(x, data = list(...))` serves a board made for core's basic front-end, holding the block and a static block for each input (below). For a path, `serve()` keeps the file in place of the JSON it would write, and opens it with the migrations of [Serialization](Rewrite-1.1.4#migrations). The new stack's `serve()` has no `plugins` argument, since core keeps no plugin or extension type of its own: a plugin's logic becomes commands and its UI a dock extension, and the notes of [Client-drawn dock and extensions](Rewrite-1.2) map each of today's nine plugins to its new home.

### Data passed to `serve()`

In `serve(new_head_block(), data = list(data = iris))`, R is handed a data frame. As a data block's state it would sit in the board's JSON, in every saved file and in every request to evaluate the block ([Wire protocol](Rewrite-1.1.9#evaluating-a-block)), and JSON carries a data frame poorly: jsonlite returns a Date or a factor column as character, and takes 7.7 s to write a 95 MB data frame as 128 MB of JSON (notes). Nor can today's `new_static_block()` carry over, since the environment it reads its data back from fits neither JSON nor a recipe. So the data blocks `serve.block()` builds for its inputs need a type whose state names data that R keeps, rather than holding the data, as a dataset block's state names a dataset in a package, and so do the tests and examples that call `new_static_block(df)` today, such as blockr.ui's and blockr.dm's example apps ([inst/examples/table-preview/app.R#L29](https://github.com/BristolMyersSquibb/blockr.ui/blob/9bd8312a3408bbcbabff2b57d1d3fd5681843c94/inst/examples/table-preview/app.R#L29), [blockr.dm inst/examples/filter-demo/app.R#L38](https://github.com/BristolMyersSquibb/blockr.dm/blob/938428bce5a488f2479034eef088f86a5053e09d/inst/examples/filter-demo/app.R#L38)).

Both methods of `serve()` therefore take `data`, a named list that R keeps for the process, beside the JSON it opens sessions from, and core's static block names an entry of it: `new_static_block("adsl")` in a board served with `data = list(adsl = adsl)`. Its state is that name, `{ "data": "adsl" }`, and its code reads `adsl`, so the board, its files and its requests carry the name while the data stays in R, and only the block's output reaches the client, as any block's does. The constructor stays a plain function of the block's state, as every block's is ([Block types in R](Rewrite-1.1.5)), and a restarted process finds the data again, since the script runs again and passes the same names. Where the process holds no entry of that name, as for a file opened by another app, the type's `validate` returns `FALSE` with a message naming it, and the block shows as invalid ([Block types in R](Rewrite-1.1.5#evaluation)). For a block, `serve.block()` builds a static block for each entry of its `data`, linked to the input the entry names, so `serve(new_head_block(), data = list(data = iris))` keeps working as written. Scripts that pass a data frame to `new_static_block()` pass it to `serve()` instead, which the switch asks only of tests, examples and dev scripts, since no package's R code calls it.

### Options

A board's options are those its parts require, declared as today through `options = default_board_options()`, the `board_options()` methods of its front-end's board class, which requests those of whatever the front-end builds on, and the `options` field of block types ([Block types in R](Rewrite-1.1.5#generics)). R collects them, with those of every type the block registry holds, keeping one per id, as `blockr_app_options()` collects them ([R/utils-serve.R#L172](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L172)), each time it opens a board, as for a file, and an option that a part requires but no installed package defines is an error naming both. What the board holds is their values: R names each option by its id, with the initial value its constructor computes, such as `blockr_option("n_rows", 50L)` for `n_rows`, and the package that ships the option defines the rest in the client, its label, category, schema, UI and what a new value does ([Board objects](Rewrite-1.1.1#options)).

### App settings

An app configures blockr as today, through `blockr_option()`: an R option `blockr.<name>` or an environment variable `BLOCKR_<NAME>`, which a deployment such as Connect sets without touching the script ([R/utils-misc.R#L247-L276](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-misc.R#L247-L276)). The packages the rewrite keeps read 56 of them, such as core's `show_conditions`, the dock's `view_tabs` and blockr.session's `session_mgmt_backend`. A setting is the app's, where a board option is the board's, so the board holds none of them, and its JSON describes the board in full. R reads the settings its own code needs where it needs them, as today, and sends the values of those the client reads with its reply to `hello` ([Wire protocol](Rewrite-1.1.9#handshake)), each package declaring which of its settings its client code reads. Core hands them to front-ends and extensions through `CoreApi` ([Front-ends and extension points](Rewrite-1.1.8#what-core-gives-a-front-end)), so client code has them passed in rather than reading a global ([State in JS](Rewrite-1#principles)).

A constructor argument that is a setting rather than state is lost to the JSON, which keeps what the board holds and nothing else. Such an argument becomes an option where it is a value, and moves to the code that calls it where it is a function. The function `new_assistant_extension()` takes as its `system_prompt` ([vignettes/intro.Rmd#L124-L153](https://github.com/BristolMyersSquibb/blockr.assistant/blob/fd5865593fd8b015d00df9238e2e622475c2a9df/vignettes/intro.Rmd#L124-L153)), which a board restored from a file loses already ([R/ext-server.R#L1229-L1231](https://github.com/BristolMyersSquibb/blockr.assistant/blob/fd5865593fd8b015d00df9238e2e622475c2a9df/R/ext-server.R#L1229-L1231)), is R because ellmer runs the agent loop in R, and becomes JS logic of the assistant extension once that loop runs in the browser ([Assistant as a client extension](Rewrite-1.4)).

The data frame figures were taken on the 4-core dev workspace with R 4.5.3 and jsonlite 2.0.0 at its defaults: a data frame of 2.5 million rows, with four double columns and one character column, is 95 MB in memory, and `jsonlite::toJSON()` takes 7.7 s to write it as 128 MB of JSON. A round trip through `jsonlite::fromJSON()` returns a Date and a factor column as character, and drops the field of an `NA` from its row.

Each shared fixture is a board as constructor calls, the file `blockr_ser()` writes for it, and the board and block registry entries R opens that file to. R's suite writes the file from the calls and opens it to those, and the client's suite writes the file again from them. Between them, the fixtures cover a block type defined outside a package, a dock board's fields, an option, and length-one vectors of both kinds.

Today's `serve.block()` matches the names in `data` to the block's inputs and, for a variadic block, gathers the entries that match none into `...args` ([R/utils-serve.R#L49-L70](https://github.com/BristolMyersSquibb/blockr.core/blob/da3fcb499549043d02d0300e05c7161f528c8729/R/utils-serve.R#L49-L70)), and the static blocks it builds follow the same matching.
