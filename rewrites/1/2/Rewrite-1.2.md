# Client-drawn dock and extensions
Status: draft. Part of [State in JS](Rewrite-1).

This part covers blockr.dock, which becomes a React app on core's JS API, and the client extension API that the DAG, the assistant, code export and session management are rebuilt on.
It builds on [Client-owned board state](Rewrite-1.1), whose core ships the one copy of React on the page ([UI modules in JS](Rewrite-1.1.7#react)), and follows the design system of [UI kit and design system for the client](Rewrite-1.7).

## Problem

The dock draws the board from R with DOM operations: `insertUI()` parks cards, `move-element` messages carry them into dockViewR panels, proxy calls add and move panels, sidebars arrive as `renderTags()` HTML and menus as `menu:sync` diffs.
Of 100 defects in the shell's history, 37 are this protocol failing ([blockr#493](https://github.com/orgs/BristolMyersSquibb/discussions/493)).

The dock's model lives in R too: views, grids, the `views$mod` grammar and the action registry (`new_action()`, `register_actions()`), so every view switch and arrangement change is sent to the session's R process.
Extensions are Shiny module pairs, made by `new_dock_extension(server, ui, ...)`, and they reach the rest of the dock through its internals, such as `sidebar_owned_by()`, the dock's actions by id and its markup (notes).
Only an app adds navbar items, through `serve()` ([blockr#494](https://github.com/orgs/BristolMyersSquibb/discussions/494)), so an extension has no way onto the navbar.

Once board state moves to the client ([Client-owned board state](Rewrite-1.1)), the dock's model is board state too.

## What must hold

1. The browser draws the dock with dockview directly, without dockViewR.
2. Views, layouts and arrangement are properties of the dock board, and no arrangement change reaches R.
3. An extension contributes panels, navbar items and sidebar sections through the dock's client API, and works on the board through core's JS API, which is enough to rebuild the DAG, the assistant, the code extension and session management on.
4. What blockr.dock offers today carries over, but for what Today drops with its reason.
5. Boards saved by today's blockr.dock open with their views and layouts.

## Proposal

- The dock is a React app on core's JS API, with the layout drawn by `dockview-react`, since React has the largest pool of components and of extension authors, AI tools write it best, and the prototype of [blockr#493](https://github.com/orgs/BristolMyersSquibb/discussions/493) ran on it.
  React draws only the chrome, while the board and commands stay in core's store.
  The dock's model (views, grids, the `views$mod` grammar, its actions) moves to TypeScript as properties of the dock board, which the dock's commands change ([Board objects](Rewrite-1.1.1#extending-cores-objects), [The dock board](Rewrite-1.2.1)), since with the client as sole owner the model is board state.
  A view's layout is stored as the dock's own grid, as today: its splits, its sizes as ratios, its tab groups with the tab each shows, and its rails ([R/dock-grid.R#L1-L32](https://github.com/BristolMyersSquibb/blockr.dock/blob/655e323c990649818627ff0ba216717396e00d5c/R/dock-grid.R#L1-L32)).
  So a board saved today opens with its layouts unchanged, and no JSON board depends on dockview, should the dock ever leave it.
  The layout that dockview itself saves was weighed for this and not chosen (notes).
  R writes the grids of a script's board as they are.
  The client turns a grid into dockview's layout when it draws a view, and dockview's layout back into a grid after each change of arrangement, with `grid_to_tree()` and `tree_to_grid()` moved from R.
- The dock board's properties hold the views, their layouts and which view is active, since a board opens on its active view and saving and restoring it keep that view.
  A layout keeps the tab that each group shows, for the same reason.
  It leaves out which group has focus, which today's grid saves as `focus`, since only one person's screen needs it, as it needs a selection.
  The dock tells its extensions which panel has focus through its API, since the assistant reads it today to tell which block the user is looking at (notes).
  Nothing syncs now, and if a relay for collaboration comes later as an add-on, it can keep each collaborator's switching between views on their own screen, as the tldraw store keeps session records "local to one editor instance, like which page you're viewing" ([tldraw store](https://tldraw.dev/sdk-features/store)), while the active view a board was saved with stays the view it opens on, so no JSON board needs migrating.
- The dock's twelve actions make edits that core's commands make already: adding, appending, prepending, inserting and removing a block, adding, changing and removing a link or a stack, and editing a block's inputs ([Board updates](Rewrite-1.1.2#commands)).
  So the dock keeps only the UI that gathers their args, the "+" menu and the editors of links, inputs and stacks, and registers commands of its own for its properties, such as adding a view, or showing a block in the active view, as blockr.dag and blockr.outline's slides do today with a `views$mod` of their own (notes).
  Everything the dock changes goes through core's deltas, so undo and save cover arrangement too, and nothing the client does to its own layout reaches R.
- Extensions are ES modules that register with the dock from their package's startup module ([Plugins](Rewrite-1.1.12#a-plugin), [Registering extensions with the dock](Rewrite-1.2.3)), the one extension mechanism, since core has none ([Client-owned board state](Rewrite-1.1)).
  An extension's logic works against core's JS API (the board, commands, requests to R), and its UI goes through the dock's contribution points as React components: panels, one per board or per block, navbar items (the API [blockr#494](https://github.com/orgs/BristolMyersSquibb/discussions/494) asks for, here on the client), sidebar sections, menus on the board, a block, a stack and the DAG's canvas, and settings ([The dock's contribution points](Rewrite-1.2.4), [The dock's navbar](Rewrite-1.2.5)).
  The dock also offers services, such as notifications and storage, where one extension can replace the dock's default ([The dock's services](Rewrite-1.2.6)).
- The dock builds its own features, such as adding blocks or showing notifications, on the same contribution points, as JupyterLab's own main menu and file browser are extensions ([extension guide](https://jupyterlab.readthedocs.io/en/latest/extension/extension_dev.html)), so an extension can do whatever the dock does.
- Extensions are few and integrate with the dock's chrome, so unlike block UIs, which keep the framework-free contract of [Client-owned board state](Rewrite-1.1), they use React directly.
  Their components render inside the dock's React tree, where hooks fail on a second copy ([React](https://react.dev/warnings/invalid-hook-call-warning)), so they are built with the same preset as block UIs, which maps `react` to the one copy core ships, the copy the dock itself uses ([UI modules in JS](Rewrite-1.1.7#react)).
  An extension with state of its own, such as the DAG's layout settings, keeps it in the dock board's `extensions`, under its id, as the dock offers it, and other extensions and the assistant change it through the commands the extension registers ([Board updates](Rewrite-1.1.2#plugins)).
  How the dock lets an extension keep that state consistent with the rest of the board, as the DAG drops a removed block's position, is [Registering extensions with the dock](Rewrite-1.2.3)'s to design, through the function its board class gives core ([Board updates](Rewrite-1.1.2#applying-a-delta)).
  So is how that state migrates, since the dock board class's `migrate` gets every property beside core's ([Board updates](Rewrite-1.1.2#plugins)).
  An extension declares the majors of the core and dock APIs it was built against.
- The DAG ([Client-drawn DAG extension](Rewrite-1.3)), the assistant ([Assistant extension](Rewrite-1.4)), the code extension ([Code export extension](Rewrite-1.5)) and session management ([Session management extension](Rewrite-1.6)) have parts of their own and are rebuilt after the dock.
  This part settles only the API they build on, and leaves libraries, agent design and their R requests to them.
- The dock places core's Edit board plugin in a panel, as it places any plugin, so that a board that mounts no DAG still edits its blocks, links and stacks ([The Edit board plugin](Rewrite-1.1.15)).
  As today, the dock itself only appends and removes a block, from a card's menu ([R/plugin-block.R#L389-L400](https://github.com/BristolMyersSquibb/blockr.dock/blob/655e323c990649818627ff0ba216717396e00d5c/R/plugin-block.R#L389-L400)).
  It has no place for stacks, and only the DAG's menus open its editors of links, inputs and stacks.
  Core's plugin is built before the dock, so it is the first plugin the dock places, and the first test of the panels of [The dock's contribution points](Rewrite-1.2.4).
- The dock draws block cards, with the header of [blockr#492](https://github.com/orgs/BristolMyersSquibb/discussions/492) and status from core, and has core mount each block's UI and output in them ([Drawing the board](Rewrite-1.1.8#what-core-gives-plugins), [Block cards in the dock](Rewrite-1.2.7)).
- A block card's sections show as the dock board's `visible` says, which keeps them by block id, as `{ "a": ["outputs"] }`, and which the card's toggles set, as today the dock keeps them itself, while on a locked board the card mounts the UI only of a block that the board lock leaves open ([Locked boards and the properties of blocks](Rewrite-1.1.11#what-a-plugin-keeps-about-a-block)).
  What else the dock locks is its own, and carries over from today: a locked dock offers no view to add, rename or remove and no panel to add or close, keeps every panel's size and place unless a deployment loosens that through the blockr options `lock_resize` and `lock_rearrange`, and offers only copying a block's id in the card's menu.
- From [blockr#493](https://github.com/orgs/BristolMyersSquibb/discussions/493), the prototype's findings carry over.
  Its transport, shinyreact, its hosting of block UIs written in R and its criterion of reusing the dock's model in R do not, since nothing in R draws UI ([Drawing the board](Rewrite-1.1.8#what-must-hold)).
  Neither does its measurement on the CEDX board: speed is benchmarked once a proof of concept of the new stack runs, with a bar of being faster than today rather than no slower ([Benchmarks of the new stack](Rewrite-1.8)).

## Open questions

- How drill-down runs as an extension that hears what renderers emit through `CoreApi` ([UI modules in JS](Rewrite-1.1.7#the-contract)) and sets block state with commands.
  Two things are open: where it keeps which block's selections go to which, as its extension state, with the UI to bind them through the dock's contribution points, such as a block menu's "Send selections to", and how a target turns a selection into its state, which belongs to the target's block class, as a hook that R answers where it needs the data, as blockr.dm's drill filter needs the dm to place a column ([Block classes in R](Rewrite-1.1.5)).
  Today blockr.viz's control bridge, an extension with no UI that the CEDX board mounts, opens the channel that blocks send selections over (notes).
  A link of its own for such edits is in the [Backlog](Backlog#control-links).
  It blocks porting blockr.viz's drill.
- Which plugins a dock app's script passes to `serve()`, which takes the app's plugins while `new_dock_board()` gives only their state ([Plugins](Rewrite-1.1.12#which-plugins-a-board-has)), and how blockr.dock spares a script from naming the dock and its extensions in both.
  Among them is whether a dock app runs core's Edit board plugin, which `serve()` gives an app by default ([The Edit board plugin](Rewrite-1.1.15#what-serve-gives-by-default)), while today's `new_dock_board()` adds no extension by default.
  So a dock board with neither the DAG nor that plugin gets no first block, since the dock itself only appends a block after another, from a card's menu.
  A board saved in a core app holds that plugin too, so a dock app without it drops the plugin as such a board opens, and tells the user that the board lost it ([Plugins](Rewrite-1.1.12#which-plugins-a-board-has)).
  It blocks what blockr.dock offers a dock app's script, and settles as this part is revised for [Plugins](Rewrite-1.1.12).
