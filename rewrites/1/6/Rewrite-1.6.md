# Session management as a storage plugin
Status: review. Part of [State in JS](Rewrite-1).

This part covers blockr.session, whose session management becomes a storage plugin that makes its storage calls from the browser.
It builds on core's storage plugins, `storage.load()` and requests ([Plugins](Rewrite-1.1.12#storage), [Drawing the board](Rewrite-1.1.8#starting-the-page)), on the dock's navbar, which draws the plugin's controls ([The dock's navbar](Rewrite-1.2.5#the-storage-plugins-controls)), and on blockr.convert, which converts what today's stack saved ([The conversion and the migration notes](Rewrite-1.8.3#who-converts)).

## Problem

The blockr.session package opens, saves, versions and shares boards from `manage_project()`, which takes the place of core's `preserve_board` plugin.
Its storage sits behind the rack layer, S3 generics over pins ([R/rack.R#L154-L540](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/rack.R#L154-L540)), and on Connect each visitor saves under their own account ([R/backend.R#L1-L15](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/backend.R#L1-L15)).
A Shiny board cannot be replaced in place, so opening another board or a new one reloads the page with `session$reload()` ([R/server.R#L235-L247](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/server.R#L235-L247)).
After the reload, `rack_loader()`, a `board_loader()` for `serve()`, builds the board that the URL names, and it fetches and deserializes the record twice for each page: once at the page's GET and once as the websocket connects ([R/server.R#L1179-L1289](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/server.R#L1179-L1289)).
With the board held by the client ([Client-owned board state](Rewrite-1.1)), only two steps of this need R: exchanging the visitor's credential, which only the content's process receives, and converting what today's stack saved.
The rest is calls to an API.

## What must hold

1. What blockr.session offers today carries over, but for what Today drops with its reason: opening, saving, versioning, sharing, tagging, downloading, uploading and deleting boards, from a storage plugin whose controls every frontend draws ([Plugins](Rewrite-1.1.12#storage)), and with no page reload.
2. The browser drives every storage call: it calls Connect itself, and any other backend through one storage API, so that no save or listing on Connect or on a deployment's own service waits on R, and neither does opening a record that the new stack saved there.
   R takes part only where nothing else can: once per page, it exchanges the visitor's session token, which only the content's process receives, for a key, it converts a record or a file that today's stack saved, and, for setting up and testing, it serves the storage API on a pins folder of its own disk.
3. A URL names a record by its key, its owner and its version, in `id`, `user` and `version` as today, and a link made today still opens the record that it names, through `board_name` too.
4. Saving a board that no record holds creates a record under a key that the user picks, and never adds a version to another record.
5. Where the blockr option `session_autosave` is set, as today, unsaved work survives a crash of R's process, of the page or of the browser, and the same browser offers it again to the same user.
6. Records that blockr.session stored today open, and so do files of today's stack that a visitor uploads ([The conversion and the migration notes](Rewrite-1.8.3#who-converts)).

## Proposal

- Session management is a storage plugin of one class, `blockr.session-session_plugin`, named Session management, which blockr.session lists in its `._BLOCKR_MODULES_` with its module and its constructor, `new_session_plugin()` ([Plugins](Rewrite-1.1.12#a-plugin)).
  Its class in R is `c("session_plugin", "storage_plugin", "plugin")` ([Plugins](Rewrite-1.1.12#plugin-classes)).
  It keeps no state in the board, so its constructor takes no args ([Plugins](Rewrite-1.1.12#storage)).
  It runs by default wherever blockr.session is installed, so `manage_project()` goes, and a script that keeps core's storage plugin leaves blockr.session's out of the rows of `plugins` ([Plugins](Rewrite-1.1.12#storage)).
  Its method of `plugin_requests()` gives what needs R: the once-per-page request, which exchanges the visitor's session token or opens R's folder, and the conversion of what today's stack saved.
- Its storage controls are those of today's piece of the navbar, in today's order ([R/ui.R#L6-L184](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/ui.R#L6-L184)):
  1. A menu named after the record's key, or "Untitled workflow" before the first save, with the ten most recent records, "All workflows…", "New workflow" and "New in a new tab".
  2. A button that says how many drafts wait, such as "2 drafts", while any do.
  3. The save status, such as "Not saved", "Just now" or "5 mins ago", and "Saved as draft" or "Autosave failed" once the plugin writes drafts.
  4. A menu named Save, with Save, which reads "Save…" before the first save, "Save as new workflow…", Download, "Version history" with the last three versions and "All versions…", and "Share…".

  Save and "Save as new workflow…" carry the shortcuts Mod+S and Mod+Shift+S, which every frontend binds ([Plugins](Rewrite-1.1.12#storage)).
  The controls call a record a workflow, as today's do, and the DAG's panel is named "Workflow", as today's extension is ([Client-drawn DAG](Rewrite-1.3#proposal)), since both name the user's board ([Glossary](Glossary)).
  For a visitor who is signed in, a status with the visitor's initials follows those controls, in place of today's avatar, a navbar item of its own ([R/avatar.R#L23-L53](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/avatar.R#L23-L53)), while `avatar_navbar_item()` returns the navbar item that places that status apart.
  A dock app that appends that item to its `navbar`, as today's appends the avatar, keeps the status after the options button, where today's avatar sits ([The dock's navbar](Rewrite-1.2.5#what-the-bar-holds)).
  Its workflows menu names the record by its key rather than by the board's name, which no storage plugin keys a record on, and a dock app leaves the board's name out of its bar, so that the bar shows one name ([The dock's navbar](Rewrite-1.2.5#the-docks-own-parts)).
  Core's basic frontend heads its toolbar with the board's name, beside the workflows menu, so that it shows both, since the board's name and the record's key name different things ([Drawing the board](Rewrite-1.1.8#cores-basic-frontend)).
  The plugin sets no board's name as a record opens, where today's sets it from the record's title, since the record holds the board with the name it was saved with.
  A row of the workflows menu opens its record in place, since a control has no second action, while the dialog behind "All workflows…" keeps the link that opens a record in a new tab.
  The search over records lives in that dialog alone, as today's second search does, since core's three kinds of control hold no text field, and a menu holds a fixed set of rows, so the workflows menu loads no more rows as it scrolls ([Plugins](Rewrite-1.1.12#storage)).
- The plugin draws what its controls cannot hold in dialogs of its own, with blockr.ui's components ([Plugins](Rewrite-1.1.12#storage)).
  "All workflows…" and "All versions…" open the records with their versions, with the search and the table that loads more rows as it scrolls, as today's "Manage Workflows" does.
  "Share…" opens the sharing settings.
  Save before the first save and "Save as new workflow…" ask for the record's key, as today's "Choose a workflow ID" does.
  At the first save, the field suggests a key made from the board's name, such as `sales-review` for "Sales review", where today's suggests the board's id, so that the two names start out alike.
  The drafts button opens the drafts.
- A URL that names a record makes the plugin's `storage.load()` resolve with the text of that record's board.
  Core opens that board in place of the script's board, before anything is drawn or evaluated ([Drawing the board](Rewrite-1.1.8#starting-the-page)), so `rack_loader()` goes.
  Where the record does not load, core opens the script's board and tells the user why, where today's loader gives a cleared board without a word.
  A record that the user opens later, from a menu or a dialog, opens through `core.store.open()`, with no reload, and the plugin updates the URL in place, with the record's `id`, `user` and `version`, keeping the URL's other parameters as today.
  A page whose URL names no record opens the script's board as R sent it ([Defining a board in R](Rewrite-1.1.3#the-opening-board)), where today's loader clears its blocks, so a deployment that wants an empty start serves an empty board.
  "New workflow" opens that board again, through what `CoreApi` gives plugins to open the board that R sent, with no reload, and drops the record from the URL, so that it gives what a page whose URL names no record gives, blocks included, as today's New does in an app that passes no loader to `serve()`, while today's `rack_loader()` clears them ([Backlog](Backlog#an-empty-new-and-new-in-cores-storage-plugin)).
  "New in a new tab" opens the app's URL without a record in a new tab.
  Under the load lock, core calls no `storage.load()`, and the controls leave out what opens a board ([Plugins](Rewrite-1.1.12#storage)).
- The controls save the JSON board that `core.store.save()` writes ([Serialization](Rewrite-1.1.4#files)).
  Save adds a version to the record that the plugin opened, unless the record's last version holds the same content hash, which the plugin reports as "No changes to save", as today.
  A board that no record holds asks for a key at its first save, which creates the record and fails where the key is taken (condition 4).
  "Save as new workflow…" creates a record under a key that the user picks, suggesting the key with `-copy`, as today, and moves the URL to it.
  It opens nothing, since the board on the page is the one that the new record holds.
  The plugin keys a record on neither the board's name nor the board's id ([Plugins](Rewrite-1.1.12#storage)).
  A record's key is fixed once the user picks it, as today, since a URL and every link to the record name it by its key, and since some backends cannot rename a key at all (notes).
- The rack layer becomes a storage API of named operations, each with JSON args and a JSON reply, such as `list_records`, `record_versions`, `read_version`, `create_record`, `add_version`, `delete_version`, `delete_record`, `capabilities` and `user`, with sharing and the search of users behind capabilities, as today's generics have them (notes).
  The blockr.session package ships a description of the API, such as an OpenAPI file, and its vignette documents the API in place of today's on a backend of one's own ([vignettes/custom-storage-backend.qmd](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/vignettes/custom-storage-backend.qmd)).
- In the browser, the plugin reaches a backend in one of two ways.
  It calls Connect directly, on the content's own origin, with the visitor's key.
  It calls any other backend through one client of the storage API, which sends each operation as `POST <base>/<operation>` to a service that speaks the API.
  The blockr option `session_mgmt_backend` names such a service by its URL, so that a database, S3 or other storage, such as the PocketBase that [blockr.session#27](https://github.com/BristolMyersSquibb/blockr.session/issues/27) asks for, sits behind a service of the deployment's own, in any language, which also keeps the credentials of that storage out of the browser.
  Without that blockr option, the plugin uses Connect where the visitor has a key.
  No storage call to Connect or to such a service goes through R, so the app's own Connect key goes, since it works for every visitor and so cannot go to the browser (Today).
  The browser's own storage holds no record, since it keeps a record in one browser alone, which may clear it.
  The plugin takes the initials of the user who is signed in from the backend, from Connect's API with the visitor's key, or from the storage API's `user` operation where a service gives one, so that R hands over the key alone.
- For setting up and testing, R serves the storage API itself, on a pins folder of its own disk, through today's methods of the rack generics for folder boards: `pins::board_local()`, unless the blockr option `session_folder` names another folder, as `session_mgmt_backend = pins::board_folder()` does today.
  The plugin uses it where R runs off Connect and `session_mgmt_backend` is unset, as today's `user_pins_board()` falls back to a local board.
  The blockr.session package registers the API's endpoint with Shiny's `session$registerDataObj()` as the plugin's once-per-page request runs, and that request's reply gives the endpoint's URL, so that the client sends R the operations over HTTP, as it sends them to any service (notes).
  Every visitor of an app shares that one folder, as today's local board is shared, so it suits setting up and testing, while a deployment for many visitors uses Connect or a service of its own.
- Where the plugin has no backend, as on Connect for a visitor without a key, such as one who is not signed in, its controls are Save, which saves a download, Open, which opens an upload, and "New workflow", beside the drafts button.
  A status says why no records show, with a tooltip that names what is missing: a Connect sign-in, or the blockr option `session_mgmt_backend`.
  Open converts a file of today's stack through R, as an upload does.
- Where the blockr option `session_autosave` gives an interval in seconds, the plugin writes a draft of unsaved work at that interval to the browser's own storage, from its class's `start`, which follows the board ([Board updates](Rewrite-1.1.2#opening-a-board)).
  A draft holds the JSON board, the record that the board was opened from, if any, the app, the user who is signed in, if any, and the time it was written.
  So a draft costs no call to a backend, and works with every backend and without one.
  A later page offers the drafts of the same app and the same user through the drafts button.
  The draft that the user restores opens with `core.store.open()`, with no reload, and the record that it was opened from stays the open record, so that Save adds a version to that record, as today.
  A draft goes once the work it holds is saved, once the user discards it, or once it is older than `session_draft_ttl` days, 7 by default.
  The browser keeps a draft on its own machine, so only that browser can restore it, while today's drafts open on any device (notes).
- Once per page, R exchanges the visitor's session token, which Connect attaches to the requests that reach the content's process, for a visitor-scoped API key through the Visitor API Key integration, and hands the key to the browser.
  The key carries only the visitor's own rights, capped by the role an administrator sets ([Connect integrations](https://docs.posit.co/connect/user/oauth-integrations/)).
  The plugin asks R through a request of its own as its `storage.load()` runs, which core sends though no board is open yet.
  The request's reply gives the visitor's key, where Connect sent a token, or the URL of R's folder, where R serves one (above), and the plugin waits for the reply there only where the URL names a record.
  Under the load lock, where core calls no `storage.load()`, the plugin asks as its `start` first runs.
  R's function for that request reads the token from the headers of the HTTP request that opened the session, which core passes it in the reserved argument `headers`, as the transport gives them, so that reading the token needs nothing of Shiny's session.
  The browser keeps the key in the page's memory alone, as the assistant keeps a visitor's own key ([Model access](Rewrite-1.4.1#how-a-call-is-authenticated)).
- A record that blockr.session stored today, or a file of today's stack that a visitor uploads, converts as the plugin opens it, through a request that R answers with blockr.convert ([The conversion and the migration notes](Rewrite-1.8.3#who-converts)).
- Its controls take the place of core's Save and Open, which save a download and open an upload.

The storage API holds what the controls and the dialogs use, as today's generics give it: the records (`rack_list()`), a record's versions (`rack_info()`), reading a version (`rack_download()`), creating a record and adding a version (`rack_create()`, `rack_append()` and `rack_upload()`), whether a key is taken (`rack_exists()`), a version's content hash (`rack_content_hash()`), deleting a version or a record (`rack_delete()` and `rack_purge()`), the capabilities (`rack_capabilities()`), and the access type, the shares and the search of users (`rack_acl()`, `rack_set_acl()`, `rack_share()`, `rack_unshare()`, `rack_shares()` and `rack_find_users()`).
Today's `rack_rename()`, `rack_name()`, `rack_tags()` and `rack_set_tags()` go, since no control uses them once the plugin sets no board's name, and so does the `draft` of `rack_create()` and `rack_records()`, since drafts leave the backend.
Connect's API takes a new `name` for a content item ([Connect's API](https://docs.posit.co/connect/api/)), but pins finds a pin by its owner and `name`, so a renamed key would leave every URL and link that names the record by its old key opening nothing.

A record is a pin written with `pins::pin_upload()` from the serialized board, with `format = "v1"` and a `content_hash` in its metadata, and with the pin tag `blockr-session` ([R/connect.R#L369-L412](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/connect.R#L369-L412)).
A pin without that tag refuses to open as a record ([R/pins.R#L324-L360](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/pins.R#L324-L360)).
On Connect, the Connect tag goes through Connect's tag API, and shares through its permissions API.
Connect gives sharing, visibility and the search of users only to a backend on the visitor's own key ([R/connect.R#L414-L431](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/connect.R#L414-L431)).
On the app's own key, today's second tier, every visitor saves under the publisher's account, so that each visitor lists, opens and overwrites the records of all the others ([R/backend.R#L60-L70](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/backend.R#L60-L70)).
Pins has clients for R and Python only, and npm has none, so the Connect backend writes and reads pin bundles itself, including those of records saved today.

Today's content hash is `rlang::hash()` of the R list that a save writes ([R/rack.R#L478-L480](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/rack.R#L478-L480)), which no hash of a JSON board matches.
So the first save after a record saved today opens always adds a version, the record's first in the new format, as [The conversion and the migration notes](Rewrite-1.8.3#who-converts) has it.

Today's drafts are rack records with `draft = TRUE`, written every `session_autosave` seconds when that blockr option is set and kept for `session_draft_ttl` days, 7 by default ([R/draft.R#L1-L30](https://github.com/BristolMyersSquibb/blockr.session/blob/66d950549a905066a2860c1d39da1cf6cf320bc8/R/draft.R#L1-L30)).
On Connect, each such write uploads a pin bundle, which Connect deploys as it deploys any content.
Should drafts in the browser prove too narrow, a backend can hold them again, as today's records at reserved keys do.
Connect serves every content item at a path of the server's one host, under its GUID or a vanity path ([Content settings](https://docs.posit.co/connect/user/content-settings/)), and its dashboard shows content in frames that only the same server may embed ([Embedding and cross-origin access](https://docs.posit.co/connect/admin/security/embedding-cors/)).
